# Architecture

The single design document. Every decision lives here, in the section it affects.
When a decision changes, edit the section and add one line to the Decision log at the bottom.

## Product

A multilingual blog engine, written in Rust, that runs entirely on the Cloudflare free plan.
The person running a blog is expected to have their own AI agent: they clone the repo, give the
agent a Cloudflare API token, and the agent sets up, writes, translates, themes and maintains.

- Open source, AGPL-3.0-only. Themes and blog content are not covered by the AGPL (theme exception, to be added to LICENSE notice before first release).
- One install serves one blog.
- Git holds code, default themes and guides. It never holds a user's data. Updating means
  `git pull` + `blog deploy`; a user never edits a tracked file, so a pull never conflicts.

## Principles (each one is enforced by `scripts/check` where a machine can check it)

0. **Reading and writing come first.** Every screen is judged first by how well it reads (or how good it feels to write in), then by UI/UX polish. Typography is tuned per font, book-like, never default browser values. Phones, tablets, desktops and foldables (folded and unfolded) are all first-class.
1. **Lightest and simplest that works.** Fixed budgets, see Budgets. New dependency needs a `# why` line in the workspace `Cargo.toml`.
2. **Fast and smooth.** PageSpeed 100 on mobile and desktop for every default theme. No layout shift. Animations use only `transform`/`opacity`, 150-250 ms, and stop under `prefers-reduced-motion`.
3. **English everywhere** in the repo: code, comments, paths, file names, guides. Only `locales/` and each theme's `locales/` hold other languages. Comments say why, not what.
4. **Built for AI operators.** If an AI agent can do a job by following a guide, plumblog ships a guide, not a feature.
5. **No drifting docs.** Fixed list of Markdown files (see Documentation). Anything a machine can generate from code is generated.
6. **Heavy work happens off the Worker.** The browser (admin) or the user's machine (CLI) does expensive work; the Worker validates, stores and serves.
7. **No hard-coded text.** Every user-facing string, English included, lives in a locale file (`locales/` for core and admin, the theme's own locale files for theme text). Code and templates only reference keys. Locale files: TOML sections nest keys; a plural message is a table of CLDR forms (`{ one = "{count} post", other = "{count} posts" }`) chosen by the `count` argument, with exactly the forms the language needs; `{name}` arguments are filled as plain text and escaped by the template layer; a missing key falls back to English, then shows the key itself. Rust names keys only with `key!("literal")` (the `Key` type has a private field and Rust lookups take `Key`; only the theme runtime may pass template strings); keys built at runtime, like month names, are listed as literals in full. In templates `t` may only be called directly, and a key built at runtime (`t("a_" ~ x)`) declares every value in `{# i18n: a_one a_two #}` on the line above. `scripts/check` fails on a used or declared key missing from `en.toml`, an undeclared dynamic key, `t` used as a value, a non-literal `key!`, a message missing or extra in another language, or wrong plural forms. Each render returns the keys found in no language; the Worker logs them as `i18n.missing_key` in its own log, not the system log, which never writes per page view.
8. **No hard-coded layout.** Core produces data and semantic content; every reader-facing page structure (what appears, where, in which order) is defined by the theme's templates. Core ships no reader HTML layout of its own beyond the default theme.
9. **Small core, extensible edges.** Core contains only what a working blog needs. Themes and declarative plugins add the rest (see Plugins and options); complex needs use the API and webhooks from outside.

## Platform

| Need | Cloudflare service | Notes |
|---|---|---|
| Public site, admin API, MCP | One Worker (Rust, `workers-rs`, wasm) | 10 ms CPU per request on free plan |
| Posts, users, settings, sessions | D1 | FTS5 for search |
| Images, theme bundles | R2 | |
| Admin JS/CSS, default theme assets | Workers static assets | |
| Rendered pages | Cache API | Cache keys include a site content version that every publish bumps, so no purge calls. Cloudflare docs only promise working cache operations on custom domains; behaviour on `*.workers.dev` is unconfirmed and must be measured (issue #8). The blog works either way: without cache every view is rendered (measured locally in workerd: about 0.06 ms wasm CPU per page with sample content; a cache hit costs about the same, so the cache mainly saves D1 reads). Each response says `x-plumblog-cache: hit|miss|bypass`; a failing cache is bypassed, never an error. Free plan: cache calls share the 50-per-request subrequest budget |
| Scheduled jobs | One Cron Trigger, `*/10 * * * *` | `crates/worker` `jobs::run` dispatches by scheduled time (UTC): every run publishes due posts (at most 14, the rest 10 min later, so the run fits the 50-subrequest cap), then sends due webhook deliveries in what is left; the 03:10 run also prunes the system log and old deliveries. Each job is independent and logs its own failure. Every `blog deploy` sets this cron through the API (`deploy::CRON`; a test checks this row and `tools/wrangler.dev.toml` agree) |
| Spam protection | Turnstile | Login after failures, comments |
| Analytics | Cloudflare Web Analytics | Not built into admin; an AI guide fetches numbers |

Free-plan rules that shape the design:
- Markdown is rendered to HTML **on save**, stored, and cached. Reading a post never parses Markdown.
- Password hashing uses WebCrypto PBKDF2 (argon2 in wasm exceeds 10 ms).
- No per-view database writes.

## Code layout

One crate per module, each with a small public API, so a module can be fixed, upgraded or replaced without touching the others. Dependencies only point down the list; `scripts/check` enforces the allowed graph.

```
crates/model      shared types, ids, errors, permissions table; no I/O
crates/markdown   Markdown -> HTML, TOC, excerpt, heading ids (pulldown-cmark + own extensions)
crates/i18n       locale files, lookup, plural rules
crates/auth       password scheme, passkey verification, sessions, roles; crypto behind a trait
crates/syslog     system log event types and the logging interface
crates/store      storage traits (posts, users, media, settings, log...) + in-memory impl for tests
crates/webhook    outgoing webhooks: payloads, signing, secret sealing, URL guard, retries; no I/O
crates/render     theme runtime: minijinja templates, template data, theme/plugin options
crates/worker     wiring only: routes per feature (pages, api, mcp, media, cron), D1/R2/cache adapters
crates/cli        the `blog` binary: setup, deploy, content and theme commands, guides
guides/           AI guides, embedded into `blog guide` and exposed over MCP
locales/          core and admin UI strings, one TOML file per language
migrations/       D1 SQL, forward-only, numbered
themes/           default themes
plugins/          default plugins (declarative, see Plugins and options)
.claude/skills/   agent skills for workflows repeated 3+ times
web/admin         admin frontend
scripts/check     the one check; pre-commit hook and CI run it
```

Each feature (posts, media, auth, search, comments, webhooks, feeds...) is a module with the same shape: types in `model`, logic in its own crate or module, storage behind a `store` trait, one route module in `worker`. Logic never calls D1, R2 or `fetch` directly, so every module is testable without Cloudflare.

Users do not need Rust: releases ship the built Worker and `blog` binaries for macOS, Linux and Windows. Only contributors compile.

## Site-specific state

- `.env`: `CLOUDFLARE_API_TOKEN` (scoped: Workers, D1, R2; never the global key), `CLOUDFLARE_ACCOUNT_ID`.
- `blog` calls the Cloudflare REST API itself (no wrangler for users). Every call is a row in `crates/cli/src/cloudflare/endpoint.rs` with the token permission it needs; `blog guide token` is generated from it. The token is read from the environment or `.env` and never printed or written; the API base is fixed, overridable (`PLUMBLOG_CF_API_BASE`) only to a loopback test server. Only GETs are retried. CLI text comes from the `[cli]` locale keys in the language of `--lang`, else `PLUMBLOG_LANG`, else the OS locale, else English; every error line carries a stable code (`crates/cli/src/text.rs`), and `scripts/check` fails on hard-coded text in CLI output or help. clap's English help, version flag and error prose are off: help is rendered from the clap command tree with locale keys, and a bad argument prints `cli.args_invalid` with the argument as data (exit 2). The Worker leaves the `[cli]` tables out of the locale text it embeds.
- `backups/`: database dumps `blog deploy` and `blog backup` make, `<utc>-<database>.sql`, mode 0600, and `blog backup`'s media copy under `backups/media/`. Ignored by git, like `.env` and `site.local.toml`; `scripts/check` fails if any is tracked. Backup policy: every deploy takes a Time Travel bookmark (free plan: any minute of the last 7 days); it also dumps the database (below) only when migrations are pending or with `--export`, because every dump reads every row and D1 counts reads against a daily limit (5 million rows on the free plan).
- The dump (`crates/cli/src/dump.rs`), written by `blog deploy` and `blog backup`, is plumblog's own: D1's export endpoint refuses our database ("Export is not supported for virtual tables, including databases with virtual tables", developers.cloudflare.com/d1/best-practices/import-export-data/; `posts_fts` is one), and the documented workaround (drop the virtual tables, export, recreate) would empty search on a live site. Read through the query API, so the database keeps answering. Layout, as D1 import takes it (no `BEGIN`/`COMMIT`): a header comment with the Time Travel bookmark taken just before (the dump is read page by page while the site runs, so it is not one instant; the bookmark is), `PRAGMA defer_foreign_keys = true;`, then every table of `sqlite_master` (with `d1_migrations`; never `sqlite_*`, `_cf_*` or a virtual table's FTS5 shadow tables `<vt>_data|idx|content|docsize|config`) with its rows, parents before children by `PRAGMA foreign_key_list`, virtual tables as their `CREATE VIRTUAL TABLE` and their rows with `rowid` (`SELECT rowid, *`, columns from `PRAGMA table_info`); a rowid table without an INTEGER PRIMARY KEY column writes its `rowid` too, so rowids survive and a split row's `UPDATE`s hit it. `posts_fts` (rowid = `posts.id`, `dump::FTS_OF`) is not read on its own: each page of `posts` reads, in the same batch (one D1 transaction), the `posts_fts` rows whose rowid is among that page's posts, and writes those of the posts it wrote, so a post edited mid-dump keeps matching search text (limit: a search row with no post is not kept); then indexes, views and triggers in `sqlite_master` order; last, `-- rows "<table>" <n>` per table and `-- end of plumblog dump`. Rows are paged by `rowid`, or by the primary key as a row value for a `WITHOUT ROWID` table, the next page after the last key; a page reads at most 1000 rows and stops after the row whose SQL crosses 512 KiB (window sum in the query), so a reply is at most that plus one row; a page cut by bytes asks for that many rows next. Values are SQLite's `quote()`, except TEXT with a NUL (`quote()` cuts there: `CAST(X'..' AS TEXT)`) and finite REALs, read as JSON numbers (exact; `serde_json` `float_roundtrip` in `blog` only) and written as an integer mantissa scaled by powers of two, because SQLite parses `quote()`'s 20 digits back exactly only with a long double (measured: about half of random doubles were off on arm64 macOS); `-0.0` comes back `0.0` (SQLite's text and JSON lose the sign). Every `CREATE TABLE` comes before any row (a parent row may be written while a later table is read). Each statement stays under D1's 100,000-byte statement limit: a row over it is inserted with its largest TEXT and BLOB values empty (`''`, `X''`), then each is appended by `UPDATE <t> SET c = c || <piece> WHERE <rowid or primary key>` (a BLOB as `CAST(c || X'..' AS BLOB)`, since `||` yields TEXT; pieces cut between UTF-8 characters, never inside a doubled quote), FTS5 rows too (an FTS5 `UPDATE` re-indexes); only a key too long to name in a `WHERE` stops with `backup.row_too_large` (table and key named) and no file. Consistent by FOREIGN KEY (D1 checks keys at the end of the import, so one orphan fails all of it): the values of every column a key points at are kept as written, and a row naming a parent the dump lacks (added after that table was read) brings the parent along, read then, with the parent's own missing parents; if the parent is gone the row is left out and counted in a warning (`cli.backup.left_out`). After the rows, `sqlite_sequence` (AUTOINCREMENT high-water marks), read then, as data, not SQL: `-- sequence "<table>" <seq>` lines before the row counts, so the import never writes `sqlite_sequence` (D1 may refuse it, which would fail the whole import). The file is written as `<name>.blog-part` and renamed when complete.
- `site.local.toml` (`crates/cli/src/state.rs`): account id, Worker name, D1 name and id, R2 bucket, origin, custom domain and whether it has passed a smoke check, Turnstile site key, the placeholder version, the script marker, the D1 `site_id`, applied migrations, the last Time Travel bookmark and a failed migration with its bookmark, the last `blog backup` record, and the last 20 deploy records (time, version, previous version, bookmark, export file, migrations applied, the bundle's migrations, outcome, smoke result) and rollbacks (restores from a file included, with their bookmark and outcome). `blog setup`, `deploy`, `rollback`, `backup` and `restore` each hold `.blog-deploy.lock` for the whole run, and every write is read-modify-write (`state::update`: reload the file, apply only that step's change, save), so an edit made meanwhile is never overwritten by an older copy. Never the token, a secret or the setup code (`state::save` refuses text containing one). Written atomically (temp file, rename), mode 0600. Ignored by git. Cloudflare stays the truth: `blog` looks every resource up by name again, so a lost file costs nothing; a folder belongs to one site (a different `--name`, `--domain` or account is refused, `setup.state_mismatch`).
- No `wrangler.toml` for users: `blog` makes every call itself. Only contributors use wrangler (`tools/wrangler.dev.toml`).
- `blog setup [--name <worker>] [--domain <host>] [--no-turnstile --yes-i-understand]` (`crates/cli/src/setup.rs`) holds `.blog-deploy.lock` and is idempotent: each step finds by name before creating (and lists again when a create fails, since a lost reply or a concurrent run may have made it), and `site.local.toml` is written after each step, so a re-run resumes and never duplicates. Order: verify the token; find the origin (`https://<worker>.<subdomain>.workers.dev`, or with `--domain` its zone, the host then each parent, before anything changes; none is `setup.zone_not_found`); an existing script of that name must be ours, also before anything changes (below); D1 `<worker>`; R2 `<worker>-media`; migrations; a placeholder Worker (503, no body) so secrets can attach before `blog deploy`, and its workers.dev address; `WEBHOOK_KEY`; Turnstile widget `plumblog-<worker>` (managed, the origin's host) and `TURNSTILE_SECRET`; the custom domain; settings `origin`, `turnstile_site_key`, `site_id` with the Worker store's own SQL (`crates/cli/src/d1.rs`); the setup code. Secret values are never printed or stored locally and are hidden in every API error. Refusals that change nothing: an existing D1 with tables but no `d1_migrations` (`setup.database_foreign`); a stored `origin` that differs from the computed one, unless `--domain` or `--change-origin` was given (`setup.origin_change_unconfirmed`), so a lost state file cannot move the site; two widgets with the site's name (`setup.turnstile_ambiguous`); a script of that name that is not ours (`setup.script_foreign`): ours means its `PLUMBLOG_SITE_ID` plain-text binding (read from `GET .../scripts/<name>/settings`) equals `script_marker` in state, or carries a marker while the folder has none (lost state), or has none while the folder recorded a placeholder or deploy for it (setups older than the marker, which get a marker in state that the next deploy adds). The marker is a binding because neither the upload metadata docs nor wrangler 4.160.0 send script tags; it is saved before the placeholder upload, so a lost reply still leaves the script recognisable, and when an adopted script was never deployed by `blog` (no deploy record, no `DB` binding) its active version is recorded as the placeholder. A migration whose SQL ran but whose `d1_migrations` row failed is `setup.migration_unrecorded` (otherwise as a failed one). Only Cloudflare's code 10007 means a script is missing; any other error stops rather than risk uploading the placeholder over a real Worker.
- `blog deploy [--export] [--build | --bundle <dir>] [--allow-older] [--theme-default]` (`crates/cli/src/deploy.rs`) needs a set-up folder, holds `.blog-deploy.lock` (one deploy or rollback per folder) and refuses while a failed migration is recorded. Order: verify the token; the bundle (`--bundle`; `--build` runs `scripts/build-bundle target/deploy-bundle` in the repo; otherwise the release bundle the binary was built for, see Release; a dev build without either flag refuses with `release.dev_build` before any call); its migrations checked against `d1_migrations` (a bundle lacking one the database ran is older code than the database: `deploy.bundle_older` unless `--allow-older`); backup (above), written to the deploy record before anything changes; the bundle's pending migrations as setup runs them (a failure stops before any code upload); static assets (upload session with a manifest of 32-hex SHA-256 prefixes, then only the buckets Cloudflare asks for, base64, under the session JWT, never the API token); a new version through the Versions API (worker-build's modules, bindings `DB`, `MEDIA`, `ASSETS`, `CF_VERSION_METADATA`, `deploy::COMPATIBILITY_DATE`, the assets completion JWT and root `_headers`, secrets kept with `keep_bindings: ["secret_text", "secret_key"]` and `WEBHOOK_KEY` (and `TURNSTILE_SECRET` when Turnstile is on) as `inherit` bindings under `?bindings_inherit=strict`, as wrangler's `versions upload` does, so a missing secret fails the upload); the active version read as the previous one (a reply without one stops the deploy: setup always leaves the placeholder); the new one deployed at 100%, then the active version read back when the reply was lost; a smoke check: `/healthz` must answer 200 with `x-plumblog-version: <new id>`, then `/` 200, retried with backoff, calls and waits together within 60 s; a failed check deploys the previous version again (migrations stay: they are compatible by rule) and fails with `deploy.smoke_failed`; then the cron (a failure leaves the deploy standing: `deployed_cron_failed`, run deploy again). Record outcomes: `failed` (nothing switched), `migration_failed`, `deployed`, `deployed_cron_failed`, `deploy_uncertain` (switch sent, active version unreadable), `rolled_back`. Every run that got past the bookmark writes `system.deploy` and `system.migration` log rows (failures too); a failed log write is reported, never fatal. Before any change it reads the serving version's pushed theme and carries it to the new version (see Themes); `--theme-default` drops it.
- Version header: the Worker reads its version id from the `CF_VERSION_METADATA` binding and sends it as `x-plumblog-version` on `/healthz`; without the binding there is no header.
- `blog rollback [--to <version-id>]` deploys the previous version of the newest record that may be serving (`deployed`, `deployed_cron_failed`, `deploy_uncertain`), or one of the script's recent versions, at 100%, then runs the same smoke check; if that fails, the version from before the rollback is deployed again. The setup placeholder is never a target (`rollback.placeholder`): neither its recorded id (`placeholder_version`) nor any version without the `DB` binding (read with `GET .../versions/<id>`, `resources.bindings`), since every secret put or delete makes a new version of the placeholder's code. deploy's older-code guard applies too: a target whose deploy record lists bundle migrations lacking one in `d1_migrations`, or with no record (not deployed by `blog` from this folder), is refused (`rollback.older`) unless `--allow-older`, which prints a warning instead. `blog rollback --db <bookmark> --yes [--clear-failed-migration]` is a Time Travel restore: it overwrites the database and cancels running queries, so it refuses without `--yes` (`rollback.db_unconfirmed`); it prints the restore and Time Travel's `previous_bookmark` (which undoes it) before saving state, clears the failed migration only for that migration's own bookmark or with the flag.
- `blog restore <file.sql> --yes [--bundle <dir> | --build] [--allow-other-site]` (`crates/cli/src/restore.rs`) replaces the database with a dump (`blog backup`, `blog deploy --export`) of any age, holding `.blog-deploy.lock`. Nothing changes before step 4, and without `--yes` it stops after the plan (`restore.unconfirmed`). 1: the file, read locally: an SQLite text dump that creates `d1_migrations` and `settings` and ends with the dump's row counts (else `restore.not_a_backup`); its `site_id` setting and migration names are read with a small SQL tokenizer (column positions from the `INSERT`'s list or the dump's `CREATE TABLE`). 2: read-only checks: the live database is ours, its `site_id` is the dump's (`restore.other_site` unless `--allow-other-site`), and every migration in the dump is in the bundle, resolved as deploy does (`restore.backup_newer`). 3: the plan (file, date from its name, migrations to run again). 4: a Time Travel bookmark, saved as a `rollbacks` record (`kind = "file"`, outcome `started`) before the first change, and the undo command `blog rollback --db <bookmark> --yes`. 5: D1 import as wrangler 4.160.0 `d1 execute --file --remote` does it: `init` with the hex MD5, the bytes `PUT` to the presigned `upload_url` (no token, HTTPS only, the reply's `ETag` must be our MD5, else `restore.upload_mismatch` and no `ingest`), `ingest`, `poll` until `complete` for at most 30 minutes; the file is `DROP ... IF EXISTS` for every trigger, view, index, virtual table and table `sqlite_master` lists (never `sqlite_*` or `_cf_*`), read just before, then the dump; the live `sqlite_sequence` marks are read just before too (dropping a table drops its mark, so ids handed out since the backup would come back). An `error` status is `restore.import_failed` (D1 rolls a failed import back); a lost reply or timeout after `ingest` is `restore.import_uncertain`; both name the undo command. Then `count(*)` of every table the file lists must be at least its count: more is the live site writing meanwhile (comments, sessions, rate limits, the log); fewer in a table the site prunes itself (`restore::SELF_PRUNING`: sessions, auth_challenges, login_failures, system_log, webhook_deliveries) only prints `cli.restore.counts_pruned`; fewer in any other is `restore.count_mismatch` (names the tables and the undo command, outcome `count_mismatch`), returned only after steps 6 and 7 still ran, so the database matches the code and no stale page is served until the owner undoes it. Then, in one batch query of its own, each table's mark is raised to the higher of its live and dumped value; a refusal (D1 writes to `sqlite_sequence` are unverified) prints `cli.restore.sequence_warning` (ids may be reused) and a `system.migration` log row, and the restore still succeeds. 6: a recorded failed migration is cleared (the file replaced that database), then deploy's runner applies the bundle's migrations the dump lacks; a failure records the restore's own pre-import bookmark as the failed migration's bookmark (`setup::apply_migrations_undoing_to`), not the one taken after the import (that holds the old backup), so the error, `blog deploy` and the printed undo all name the same command, and running it clears the failure. 7: the content version is set above its restored value and 1000 above the higher of the values read at step 2 and again just before the import (the site keeps bumping it during the upload), so no page cached before the restore is served; the record's outcome and a `system.migration` log row close the run.
- Release bundle (what `blog deploy --bundle` reads; `scripts/build-bundle` makes it, releases ship it): `worker/` is worker-build's `--release` output (wasm-opt included; `package.json` `main` names the main ES module, every top-level `.js`/`.mjs` and `.wasm` is uploaded as a module) and `assets/` is the static assets root laid out by `scripts/assemble-assets`, the same layout `scripts/worker-test` serves: `theme/minimal/`, `plugin/<name>/`, `admin/`, and the admin's `_headers` at the root (sent as assets config, not as a file); `migrations/` holds the D1 migrations this Worker expects, which deploy runs (not the CLI's own). Symlinks are refused. A release archive adds `bundle.json` (`version`, `commit`, `files`: path to SHA-256). Asset hashes: SHA-256 of base64(content) plus the extension, first 32 hex characters (wrangler's input, BLAKE3 there).
- Turnstile is on by default. `--no-turnstile` needs `--yes-i-understand` (`setup.no_turnstile_unconfirmed`) and prints why: without it, sign-in floods can lock sign-in in 15-minute windows, and comments stay off. On a site that had it, it really turns off: the `turnstile_site_key` setting is deleted with the Worker's `delete_setting` SQL (content-version bump), the `TURNSTILE_SECRET` secret deleted (`DELETE .../secrets/<name>`, Workers Scripts Edit) and the site key cleared from state; the widget `plumblog-<worker>` is kept and named, to delete in the dashboard or reuse.
- Setup code: only while `users` is empty; 20 readable characters (100 random bits), printed once, stored as `setup_hash_json(<sha256 hex>)` with a 24 h expiry by the Worker's `put_setup_code` SQL, guarded by "no user exists" in the same statement. A re-run before the owner exists replaces it; with an owner it says so and writes nothing.
- Worker secret `WEBHOOK_KEY` (base64 of 32 random bytes) seals webhook secrets; `blog setup` creates it once and never rotates it. Without it webhooks cannot be created or sent (`webhook.key_invalid`, logged); losing it means re-creating every webhook's secret. `TURNSTILE_SECRET` is put when missing, or when the widget was just created (an older value would be stale).
- Everything else (site name, languages, menu, theme choice, colors) is stored in D1 and edited in the admin.

## Storage

- A migration must stay compatible with the previous Worker version: a deploy migrates before it switches code, and a rollback runs old code on the new schema. Add columns and tables; never drop, rename or narrow one a released Worker reads.
- Migrations are applied by `blog` (`crates/cli/src/migrations.rs`, shared by setup and deploy) and tracked in wrangler's own `d1_migrations` table (same columns, one row per file name, number order), so a contributor's wrangler agrees. The D1 REST query is not documented as atomic (only the Worker binding's `batch()` is), so: a Time Travel bookmark first whenever anything is pending, one request per migration, its row written only after that request succeeded, and on failure a stop that names the migration, Cloudflare's error, the bookmark and `blog rollback --db <bookmark> --yes`, with no settings written after it. The failed migration and its bookmark stay in `site.local.toml`: until `blog rollback --db` or `blog setup --clear-failed-migration` clears them, no migration runs and that bookmark is never replaced by one of the half-migrated database. The fake API in tests runs the real files in SQLite (rusqlite, tests only).
- Schema: `migrations/`, forward-only and numbered; each index says in a comment which query it serves. Times are UTC milliseconds. Only hashes of session, token and invite secrets are stored. Webhook signing secrets must be readable, so they are sealed with AES-256-GCM under the Worker secret `WEBHOOK_KEY` (`v1:<nonce>:<ciphertext>`), shown once at creation and never returned again; rotating means a new secret.
- `crates/store` holds the traits and an in-memory store; `crates/worker/src/d1/` is the only D1 code. One contract suite runs against both, so they cannot drift.
- Every multi-row write is one D1 batch (a transaction): a post save writes the row, its tags, its search text, a revision, an automatic slug redirect and the content-version bump together, or nothing.
- Ids that leave their row (URLs, translation groups, log entries) use AUTOINCREMENT, so a deleted id is never reused.
- Posts carry a `version`; every save names the version it edited, and a stale save is refused (`store.conflict`) so the admin can offer a merge instead of silently overwriting. User records change through narrow writes (profile, password, role, disabled), never a full-row rewrite, and the last active owner cannot be demoted, disabled or deleted.
- Media in use (post body via `post_media`, filled on save, or cover) cannot be deleted; the error lists the posts.
- Search: SQLite FTS5 with `unicode61 remove_diacritics 2`, which folds Vietnamese tone and horn marks; the app folds d-stroke to `d` itself because the tokenizer treats it as a separate letter. Results are newest first, so the in-memory store answers identically.
- Lists page by keyset (last row's sort value and id), never OFFSET: D1 bills every row read, including skipped ones. One exception: reader listings (`ReaderStore::reader_posts`) keep numbered pages (`/page/N`) and use LIMIT/OFFSET, because each page is computed once per content version and then cached. Guards: a COUNT runs first, and no rows are read when the offset is at or past the count or at or past 10,000 (`READER_MAX_OFFSET`); the page itself pages over keys only (`posts_home` for the home page, `posts_by_date` for a year, `posts_listing` for a language; `post_tags_tag` and then a primary-key lookup on `posts` for a tag, sorted in a temp b-tree of that tag's posts) and reads only its own rows in full. A year outside 1..=9999 matches nothing and runs no query; `crates/worker/src/d1/reader_sql.rs` holds every reader statement and a test runs `EXPLAIN QUERY PLAN` on each against real SQLite with the migrations applied, asserting the index named in its doc and whether a TEMP B-TREE is expected (the translation lookup names `posts_group_lang` with `INDEXED BY`: the D1 planner took `posts_admin (status)` and read every published row); posts outside those years are left out of the year list. Admin and API lists stay keyset.
- Queries per reader page (cache miss): content version 1 (before the cache lookup, so also on a hit), then settings 1, theme options 1, plugins 1 when any are bundled plus 1 per enabled plugin, plus the page itself: home 2 (count, rows; 1 past the end; 0 past the offset cap); post 3 (post with tags, translations, neighbours; a page has no neighbours; a missing post 1) plus comments (posts only; a static page reads none): 1 when the site has them off, else 1 + 1 (the post's approved comments), and 2 more (Turnstile key) when the form is open; tag 3 (the tag, count, rows); archive 3 and years 1; feed 1 (bodies, tags); sitemap 3 (one statement, two ordered index reads: posts and pages, merged in the Worker; tags; years); llms.txt 2; 404 page 2 (recent posts); search 1. A redirect or a route that matches nothing makes no page query. Reader pages never write.

## Users and auth

- Two roles. **owner**: everything. **writer**: write, publish, edit and delete any post, upload media and edit any item's alt text but delete only their own media (the owner deletes any: `media.delete_any`), moderate comments, create own API tokens with writer scope. Cannot touch settings (including the site-wide comments switch), themes or users.
- Password (PBKDF2 via WebCrypto) and passkeys (WebAuthn, verified with WebCrypto). Session cookie: HttpOnly, Secure, SameSite=Strict.
- First owner: `blog setup` prints a one-time setup code; the site refuses to create an owner without it.
- Recovery: `blog admin reset` (whoever holds the Cloudflare token owns the blog). No email recovery.
- `blog admin reset [--login <owner>] --yes [--keep-tokens]` (`crates/cli/src/admin.rs`) needs a set-up folder and the token, holds `.blog-deploy.lock`, and reads before it writes: the Worker's `PLUMBLOG_SITE_ID` binding must equal `script_marker` in state and the D1 `site_id` setting must equal `site_id` in state (recorded by `blog setup`; a folder without it re-runs setup once), else `admin.reset_foreign`; a Worker with no such binding (an older setup, or a rollback to a version from before it) is `admin.reset_unmarked`: `blog setup` records a marker in state but only `blog deploy` puts it on the Worker, so the message says setup, deploy, retry; several active owners and no `--login` is `admin.reset_ambiguous` (lists them), a `--login` that is not an active owner `admin.reset_not_owner`, no owner at all `admin.reset_no_owner`. Without `--yes` it prints the plan (counts of sessions, passkeys, tokens, unused invites, and the other active owners with login, role and creation time, printed again after a reset, so an owner an attacker added stands out) and stops, `admin.reset_unconfirmed`. Then one D1 request, ordered so any prefix leaves the account more locked, never more open (the REST query is not documented atomic): password set to NULL (never verifies; sign-in answers it like a wrong password, at the same cost, where an unparseable hash would be a 500), passkeys deleted, sessions deleted, API tokens revoked (default, since an attacker may have minted some; `--keep-tokens` keeps them and says so), every unused invite that owner created, of any role and age (one made before the reset would still let someone in), the reset code (hash, then user, expiry, reset time and the `--keep-tokens` choice: a cut request leaves a hash nobody was shown and kills the previous code), and an `auth.owner_reset` log row (user id, what was revoked, `via cli`; never the code). The code (20 characters like the setup code) is printed once with `<origin>/admin/reset` and written nowhere else; a re-run replaces it. Why: the token holder already owns the Worker and its data, so the token is the right proof; the attacker is cut off when the owner acts, not an hour later when the code is used; the code is shown once so no file or log can leak it; 1 h expiry because the owner redeems it right away. Left as they are: other users, their invites and content; the CLI and guide tell the owner to rotate webhook and other secrets the admin shows and to review users and invites after a takeover. Requests in flight: every Worker write that creates a credential (session, passkey, API token, invite, password change) carries the `Proof` its request authenticated with (the session, the password hash or passkey that verified, or the reset code) and lands only if that still holds, in the same atomic write; the reset removes all of them, so a request that checked before the reset and writes after it creates nothing. If the REST request is not atomic and a write lands between its statements, the redeem undoes it: it deletes every passkey and session of the owner and revokes the tokens and deletes the unused invites (any role) created since 10 minutes before the reset time (`OWNER_RESET_SINCE_MARGIN_MS`: a request that began before the reset stamps its own start, and the CLI's clock may lead the Worker's), every token without `--keep-tokens`. Until the code is redeemed, a passkey added in such a gap still signs in; if the owner cannot redeem within the hour, run `blog admin reset` again, which removes it.
- Redeeming: `POST /api/auth/reset` (`code`, `login`, stretched `password`, `turnstile_token`) from `/admin/reset`, limited like setup codes (per address, site-wide cap, Turnstile). The hash is compared in constant time, then `redeem_owner_reset` is one atomic write (a Worker binding batch) that checks the code (stored, bound to that user, unexpired) and that the user is still an active owner, sets the password (and the login, if changed: the stretch salt holds it), deletes every session and passkey of the owner, revokes tokens and deletes invites as above, deletes the reset keys and creates this session; `auth.owner_reset_redeemed` is logged. A login another user holds fails that write (409 `store.conflict`, field `login`), so nothing changes and the code still works. If the check fails, `take_owner_reset` spends the code (an expired one is deleted too): a wrong one is counted and answers `setup.invalid`; the right one past its expiry is not counted (not a guess, so a late owner is not pushed toward Turnstile or a lock) and answers `auth.reset_expired` (the page says to run `blog admin reset` again); one whose owner was demoted or disabled since gives nothing and answers `setup.invalid`.
- Writers join through a one-time invite link the owner copies from the admin.
- User admin (`/api/v1/users/{id}/role` `{role}`, `/api/v1/users/{id}/disabled` `{disabled}`, `DELETE /api/v1/users/{id}`, `/api/v1/invites` list, create `{role, expires_at?}` and `DELETE /api/v1/invites/{id}`): `user.manage` and session only (route `session_only`; any token, an owner one included, gets 403 `auth.forbidden`), since a leaked token must not mint owners or lock them out; so none is an MCP tool. An invite code is 32 random bytes in base64url, in the create answer only (the admin makes the `/admin/invite?code=` link); only its SHA-256 hex is stored, written with the creator's session as `Proof`. Every user-admin write (invite create, role, disable, enable, delete) re-checks its actor inside the write (`store::Admin`: a guard in the same D1 batch, the memory store under its lock): the session still exists (else 401 `auth.unauthenticated`) and its user is still an active owner (else 403 `auth.forbidden`, the reason in the log), so an owner demoted or disabled while a request runs writes nothing; D1 does not say which guard of a batch fired, so a read after the refused write tells the actor's from the last-owner one. Expiry defaults to 7 days, at most 30 (`api::INVITE_TTL_MS`, `INVITE_MAX_TTL_MS`); the list holds unused invites, expired ones included, and a used one cannot be revoked (one `DELETE ... AND used_at IS NULL`; no row is 404 `store.not_found`). The last active (not disabled) owner is never demoted, disabled or deleted: 409 `user.last_owner`, checked inside the write (a guard statement in the same D1 batch, the memory store under its lock), so two owners demoting each other at once leave one. An owner may act on themself only within that rule. Disabling deletes the user's sessions and unused invites and revokes their unrevoked tokens in the same batch, so re-enabling brings none back; demoting an owner deletes their unused invites too. Accepting also requires the invite's creator to still be an active owner (a condition of the same statement), so an invite minted with a stolen session dies with that owner's access, whatever path demoted or disabled them. Deleting is refused (409 `store.conflict`) while they author any post; it deletes their sessions, passkeys, tokens and the invites they made (used ones too: `invites.created_by` is `ON DELETE CASCADE`, so the record of whom they invited goes with them), and clears their name from media uploads, revisions, used invites and log entries. Each action logs `user.changed` with `action` and ids, never the code, only after the write succeeded; a self-delete logs no `actor_id` (it would name a deleted user) and the actor's id in the field `actor`. Revoking re-checks its actor in the write like the others.
- Login rate limited; Turnstile after repeated failures. Audit log of sign-ins and privileged actions.
- Passwords are stretched in the browser (PBKDF2-SHA256, 600 000 iterations, salt `plumblog:<site id>:<lowercase login>`, so there is no salt lookup to enumerate users); the server stores PBKDF2-SHA256 of that value with a per-user salt and 1 000 iterations, inside the 10 ms budget. Changing a login needs the password, because the salt changes.
- Rate limit: attempts per hashed login (or passkey credential id) and hashed IP (IPv6 /64) in a 15-minute window, counted before the secret is checked with one atomic upsert per key (so concurrent attempts each get their own count and at most the threshold reach the check), and on success one write per key taking the attempt back (the login or credential key is cleared, the address keeps its earlier failures); the decision uses the attempts before this one: 5 ask for Turnstile (or lock if Turnstile is not set up), 20 lock. Refused attempts stay counted but never extend a lock, which ends with its window. Unknown logins cost and answer the same as wrong passwords. An address already locked is refused from one read, before the site-wide count below, so it never adds to it; then the address key is counted first; once it is locked the attempt writes nothing more (no login or credential key, no challenge), and a key that reached its lock is never rewritten (`ON CONFLICT ... DO UPDATE ... WHERE`), so a flood of random logins from one address cannot burn D1's daily write quota. Ended rows are reused, and swept 50 at a time by the first attempt of an address's window and of the site-wide window (the only sweep for attempts without an address); no cron. Turnstile settings are read only when an attempt reaches a threshold. Wrong setup and invite codes count per address with the same thresholds; anonymous passkey sign-in options count per address under their own key, 20 per window (below the site-wide cap, so one address cannot fill it).
- Site-wide cap (issue #51): per-/64 keys still let a /48 (65 536 /64s) spend D1's free 100 000 rows written a day, so every anonymous limited attempt (password and passkey sign-in, setup and invite codes, anonymous passkey options) is counted on one fixed key, `global`, in the same 15-minute window, by one statement that writes nothing once the window holds `GLOBAL_CAP` = 50. Without Turnstile that bounds sign-in writes to about 40 000 rows a day, lock log rows included (the math is at the constant); with Turnstile on, writes past the cap are bounded by solved challenges. A locked address (or one at its options limit) is refused before this count, so one address adds at most its own threshold per window. At the cap: with Turnstile fully set up (site key, secret, origin) the attempt must carry a valid token, verified before any write, and then goes through the per-address and per-key limits as usual; otherwise 403 `auth.turnstile_required`. Without Turnstile it is 429 `auth.locked` with no write until the window ends (never extended). The attempt that reaches the cap logs `auth.global_cap` once per window. Without Turnstile, many addresses (a /48 sends 5 failures from each of 10 /64s) can keep anonymous sign-in refused for every window they flood; the real protection against such lockout floods is Turnstile. Signed-in users are not subject to the cap: their session works, and re-authentication (current password for a password or login change, current password or passkey assertion to add or remove a passkey) keeps only its per-login, per-credential and per-address limits. Passkey sign-in at the cap needs one token, for the options request (issue #63; tokens are single use): its challenge is then stored under the hash of a domain-separated input (`gated`), and a sign-in presenting it at the cap consumes it, in the same single atomic take, as the gate proof instead of a token; the per-address and per-credential limits still count. It is consumed even when the attempt is then refused by those limits, like a token spent on a refused attempt. Only options that verified a token mint one; it is login-only and single use; a challenge issued below the cap still needs a token at the cap. Options stays under the cap because it writes a row, and challenges stay stored because stateless ones would lose replay protection for authenticators whose sign counter is always 0. Not the Workers Rate Limiting binding (Cloudflare's docs do not state Free-plan availability, and its counts are per location and approximate) nor a WAF rule (Free plan: 10-second periods only, per zone, not on workers.dev).
- Sessions: random 32-byte token, only its hash stored; cookie `__Host-plumblog_session` (HttpOnly, Secure, SameSite=Strict), 30 days, renewed only on API requests when less than half remains. The id rotates on sign-in and on password or login change, not on a role change: only an owner changes roles, so a role change never raises the caller's own; a password change ends the user's other sessions, a disable all of them. Every non-GET API request must carry the site's `Origin`.
- Passkeys: attestation `none`, ES256, RS256 and Ed25519 verified with WebCrypto; a small CBOR reader of our own; single-use challenges (32 random bytes, stored hashed) that expire in 5 minutes, consumed even when the ceremony then fails; user verification required; discoverable credentials, so sign-in options name no user; a sign counter that does not increase refuses the sign-in and is logged. Failed passkey sign-ins count in the same limiter, keyed by credential id and address; a disabled account's passkey answers like an unknown one. The relying party (rp id, expected origin), the host a Turnstile token must name and the CSRF `Origin` come from the configured origin (settings `origin`: canonical `https://host[:port]`, `http` only for localhost; anything else is a 500): an rp id is permanent and the Host header is the client's, so there is no fallback; without one, passkeys and Turnstile answer 503 `settings.origin_missing` while password sign-in and setup keep working, and CSRF compares with the request's own origin. An account without a password changes its login by re-authenticating with a passkey (same atomic write and session rotation as a password change; refused if a password appeared meanwhile), and cannot remove its last passkey (checked inside the delete's own write). Adding or removing a passkey re-authenticates: `current_password`, or an assertion by one of the user's own passkeys (`reauth_*` fields), limited and counted like sign-in; without either, 403 `auth.reauth_required`, so a stolen session cookie cannot plant a key that survives a password change. `GET /api/auth/me` lists the user's passkeys (added, last used). A key WebCrypto cannot import (an ES256 point off the curve) is refused at registration; one already stored fails sign-in as a counted `auth.passkey_invalid`.
- The first owner is created with the setup code (hash and 24 h expiry in settings), atomically, only while no user exists. API tokens (Bearer) use the same permission check (AI surface). Logs never hold passwords, stretched values, codes, challenges, tokens or IPs.
- API (`crates/worker/src/api`): every `/api/` request passes the same gate: `Origin` check on non-GET, then the principal (session cookie, or an API token from `Authorization: Bearer`, which skips the `Origin` check), then the route's `auth::require`. A body over its route's cap by `Content-Length` (8 KiB; 160 KiB on `/api/v1` post saves) is 413 `api.body_too_large` before it is read; a body without `Content-Length` (chunked) is 411 `api.length_required`. Errors are `{"error":"<stable code>"}` (plus `"field"` naming the request field at fault, for input errors) with a fixed status per code; details go only to the Worker log with the request id. `GET /api/auth/params` gives the sign-in page the site id (created once, race-safe), the stretch iterations and the Turnstile site key. A password or login change is one store write that also ends all the user's sessions and creates the rotated one, so a failure can never leave a login and its stretched password out of step. Internal settings (setup code hash and expiry, owner reset hash, user, expiry, time and token choice, last backup) are listed once in `store::INTERNAL_SETTING_KEYS`; anything that hands settings to a client or theme filters through `store::public_settings`.
- System log events: sign-in, sign-out, failures (password, passkey, setup, invite and reset codes), locks, passkey added and removed, password and login changes, API token created and revoked, owner reset and its redemption, user admin (invites, roles, disable, enable, delete).
- Measured (issue #9): server-side PBKDF2 x1000 in workerd about 0.09 ms; the browser stretch (600 000) about 46 ms in desktop Chromium and 62 ms in Node on the dev machine, so roughly 0.5-1 s on a slow phone.

## Content

- Posts and pages; drafts, scheduled, revisions (author recorded), trash with restore.
- Tags and series; pinned posts; cover image; excerpt (written by the author, else cut from the text at a word boundary; the length is the theme option `excerpt_words`, default 55 words); auto table of contents; reading time.
- Translations: one row per language, linked by a translation group. URLs `/<lang>/<slug>`. Missing translation shows the original with a notice. Translation itself is done by the user's AI.
- Changing a slug creates a permanent redirect automatically.
- Author pages.

### Markdown

CommonMark + GFM (tables, task lists, strikethrough, autolinks), footnotes, callouts, math (rendered to MathML), code blocks, image captions, galleries, embeds (click-to-load facade, no third-party load until clicked).

**Raw HTML in Markdown is not allowed**: tags, comments and HTML blocks are dropped, while text between inline tags stays (`<b>word</b>` reads "word"); escaping tags into visible text would litter posts pasted from the web. Revisit later only with a safe-tag allowlist. Link URLs allow only relative, `#`, `http(s)`, `mailto`, `tel`; image URLs only relative and `http(s)`.

Authoring syntax, chosen because AI agents already write it: callouts are GitHub alerts (`> [!NOTE]`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`); an image alone in a paragraph is a figure and its title (`![alt](src "caption")`) is the caption; a YouTube or Vimeo URL alone on a line is an embed; math is `$...$`, `$$...$$` or a `math` code block, rendered to MathML at save time by pulldown-latex (+~70 KB gzip wasm), so readers need no math script. Invalid LaTeX shows its source as `code.math-error` and returns a `markdown.math_invalid` warning to the editor. Author `<`/`>` become `\lt`/`\gt` before parsing and the MathML is rebuilt through a MathML Core allowlist; no `style` attribute is ever emitted, so `\color` is ignored. Excerpt and reading time count each CJK character as a word.

Code highlighting runs on the reader page: a small deferred script (<= 8 KB gzip) loaded only on pages that contain code. Nothing is highlighted at save time, so posts from the admin, the CLI and MCP all look the same.

### Images

- Encoded in the browser at upload: three AVIF sizes plus one small JPEG fallback, using a Rust AVIF encoder compiled to wasm, loaded only when the user uploads. Runs off the main thread with progress.
- Original kept in R2 for future re-encoding.
- Always `width`/`height`, `srcset`, lazy below the fold.
- Social card image = cover image, else site default. No generated cards.
- Served at `/media/<id>` and `/media/<id>/<name>` (`crates/worker/src/media.rs`, GET and HEAD; other methods 405). `<name>` is the original's file name (last segment of `r2_key`) or that of a `variants_json` entry's `key`, which serves that variant; any other name, a non-canonical id or more segments is 404. Anonymous: only media a `published` post or page uses (body via `post_media`, or cover), the reader's own test, in one D1 read (`MediaStore::public_media`); draft-only, scheduled, trashed, unused and unknown give the same empty `no-store` 404, never the theme's page. A session or token with `read` gets any item as `private, no-store` (the editor preview). The principal is resolved read-only (`api::resolve_read_only`: no session renewal, no cookie cleared), so no request writes D1 or sets a cookie. Public answers are `public, max-age=31536000, immutable`: a URL always names the same bytes, as a re-upload is a new id; so unpublishing does not recall copies browsers already hold. Body streamed from R2 with the checks of `GET /api/v1/media/{id}/original` (mime in `MEDIA_MIMES`, size = row bytes <= `MAX_MEDIA_BODY`, else 500; no object 404, logged), `nosniff`, `sandbox` CSP, `ETag` = R2's `httpEtag`. One `If-None-Match` tag goes to R2 `onlyIf` (304, no body read; `*` or a list is ignored); one `Range` (`a-b`, `a-`, `-n`) is an R2 range get (206, `Content-Range`), past the end 416 `bytes */<size>`, a multi-range or malformed one ignored (200); `If-None-Match` is decided first, so a held copy is 304 even with such a range; HEAD uses R2 `head()` and ignores `Range` (200 headers).

## Reader site

Home, pagination, tag/author/series pages, yearly archive, search (accent-insensitive; Vietnamese `d-stroke (U+0111)` normalised to `d`), related posts by tag, RSS/Atom/JSON Feed per language, sitemap, `robots.txt`, `llms.txt`, full SEO (meta, JSON-LD, hreflang, canonical), friendly 404 with suggestions, light/dark toggle.

Navigation feels instant without JS frameworks: Speculation Rules prefetch, cross-document View Transitions.

URLs: `/` and `/page/N` (home, the default language only, like the feed, `llms.txt` and the 404 page's suggestions; another language's home is #87), `/<slug>` (post in the default language), `/<lang>/<slug>` (post in another language), `/tag/<slug>` and `/tag/<slug>/page/N`, `/archive/<year>`, `/search?q=`. One URL per page: trailing slashes and `/page/1` redirect (301), and `/<default-lang>/<slug>` redirects to `/<slug>`; a post of another language at `/<slug>` is a 404, never a guess. A page number past the last page is a 404 decided from the listing's count, and one whose offset reaches 10,000 is a 404 before any query. Translations link both ways (hreflang, `x-default` = the default language's version, in the page and the sitemap); a comment form posts to `<post url>/comments`. `page`, `tag`, `archive`, `search`, `theme`, `admin` and `api` are not valid slugs. Search reads the store (one query; FTS syntax in the query is quoted away by `store::search`), keeps the first 100 characters of the query and shows the 20 newest matches, saying so when there are more; result pages are `noindex`, `no-store` and skip the page cache, since neither the query nor store changes are in its key. A query without words shows the form and makes no query. Site settings (`settings` rows, JSON values, written with `PUT /api/v1/settings/{key}`; the key rule `a-z 0-9 _ -` has no dot, so they are `site_*`): `site_title` (default: the core locale's `site.title_fallback`), `site_description` and `site_footer` (empty), `site_lang` (the default language, `en`), `site_languages` (array, default `[site_lang]`; parsed, not yet read by any page), `site_per_page` (1-50, default 10), and `origin` as before. All six are read with one query, a missing or malformed value falls back to its default (the bad ones are logged), so a fresh site renders and no stored value can break a page; every settings write bumps the content version. The store has no site clock, and no page shows a date the site never had: a feed is dated by its newest post, else by the newest settings write (`settings.updated_at`, one query), else it states no date (Atom `<updated>`, RSS `lastBuildDate` left out); the sitemap's home entry has the newest post's `updated_at`, or no `lastmod`. Posts and pages are read from D1 (`pages/reader_db.rs`); the sample site (`crates/worker/sample/`) is built only into tests and `/__seed`, never the Worker. The store keeps one excerpt per post (written or automatic), so the theme always cuts it to `excerpt_words`. Pages carry an `ETag` of content version plus engine version, so a returning reader gets a 304; 404 pages are never cached. Feeds: `/feed.xml` (Atom), `/rss.xml`, `/feed.json` (JSON Feed 1.1), 20 newest posts with full content and absolute links, default language at the root and others under `/<lang>/`; plus `/sitemap.xml` (hreflang alternates with `x-default` for translations; at most 50,000 URLs, logged when cut until a sitemap index exists), `/robots.txt`, `/llms.txt`, all through the versioned cache. Public URLs (canonical, feed and entry ids, sitemap) use only the site's configured origin (`blog setup` writes it), never the request's Host header, so `*.workers.dev` and a custom domain give the same ids; with none set they use a fixed `http://localhost` and the Worker logs `settings.origin_missing`. Feeds and JSON-LD are formats, so `render` builds them; the theme prints the meta tags (Open Graph, Twitter card, hreflang) from `page.seo`.

Comments: own system, off by default, Turnstile, moderation queue (owner and writer). Open on a post only when the site setting `comments.enabled` (owner only, default off) and the post's own switch are both on, and the post is published; no auto-close. Static pages (kind `page`) take no comments: no form, and the route answers 404. Flat list (no reader replies in v1); a post shows its newest 100 approved comments, oldest first, with a note when older ones are left out (paging later). Bodies are Markdown in a restricted mode (`plumblog_markdown::render_comment`: paragraphs, emphasis, inline code, code blocks, blockquotes, lists, absolute `http(s)` links with `rel="nofollow ugc noopener"`; headings become paragraphs, images their alt text, raw HTML dropped), rendered once at submit and stored in `comments.body_html` (rows from before that column are rendered when the page is built). Limits: name 1-60 visible characters, body 1-5,000 (line breaks normalised to `\n` before counting and storing), at most 30 links. The form posts to `<post url>/comments` (urlencoded, 64 KB cap, enough for 5,000 non-ASCII characters); the route checks form, post, limits, then `CommentGate::precheck` (read-only: an address already at its cap is refused with no write and no siteverify call), `CommentGate::verify` (Turnstile siteverify, token and sender address) and `CommentGate::record` (counts the attempt, atomically), in that order so a flood without valid tokens writes 0 rows and each limiter row costs the attacker one solved challenge, before any write, stores the comment as pending with one `comment.created` system log entry (ids only), and answers 303 to `<post>?comment=pending#comments` or `<post>?comment=error&code=<stable code>#comments`. The gate is built after the form and post checks and is Turnstile when the settings `turnstile_site_key` and `origin` and the secret `TURNSTILE_SECRET` are all set (read as sign-in reads them; half a setup is logged); otherwise it refuses everything with `comments.unavailable` (before any limit count or siteverify call) and nothing is stored. The post page shows the widget on settings alone (key and origin set), never on the secret, so cached pages follow settings changes (each bumps the content version); a page with a widget but no secret answers `unavailable` on send. A failed settings read fails the page render (not cached). A wrong token, a token solved on another host, a missing token, or any siteverify failure (network, status, unreadable answer, logged with detail) is `comments.check_failed`: never fail open. Limit: 5 attempts per hashed address (IPv6 /64) per 10 minutes, only attempts with a valid token count (failed Turnstile checks do not), in the sign-in limiter table with its own key, no migration; over it is `comments.rate_limited`. A person writes a comment or two and retries a typo; the window is long enough to blunt a script and short enough to write again soon. `?comment=` never changes the page: it is the same cached page, and theme JS shows the result line from a whitelist the template puts in the page (text only, unknown codes get a generic error), then removes the parameters from the URL. Approving a comment bumps the content version. Each moderation action leaves one `comment.moderated` entry (comment id, post id, new status, actor).

Installable web apps: the reader site (scope `/`) and the admin (scope `/admin/`) each have their own manifest and icon, so both can sit on a home screen and are told apart by color. Blog icon = the owner's site icon (uploaded in Settings; default generated from the site name on the theme accent). Admin icon = the same mark on a contrasting dark plate, named "<Site> Admin". No offline reading for the reader site; the admin caches its own shell and keeps drafts offline.

Not built: offline reading, newsletter (later), reactions.

## Themes

- Three default themes: **literary** (serif, warm paper), **minimal** (sans, monochrome, one accent), **technical** (monospace accents). Each has light and dark.
- A theme is a folder, distributed as a zip:
  ```
  theme.toml     name, version, light + dark color tokens, fonts
  style.css      uses tokens only, no hard-coded colors
  templates/     optional minijinja overrides; missing files fall back to the default theme
  assets/        images, fonts, JS
  locales/       the theme's own UI text, one TOML per language; templates call t("section.key", name=value)
  ```
- TOML is for authors only. The Worker links no TOML parser (it was about 51 KB gzip of the wasm): it loads JSON. `theme.toml`, `plugin.toml` and every `locales/*.toml` reach it converted, under the same path plus `.json` (`theme.toml.json`, `locales/en.toml.json`), one rule (`plumblog_render::convert::json_name`) and one converter (`convert::file`, behind the `toml` feature of `plumblog-render` and `plumblog-i18n`, off by default). The Worker's `build.rs` converts the embedded default theme, plugins and core locales at build time; `blog theme check`, `dev` and `push` convert the folder, so a TOML syntax or manifest type error is reported there, naming the file and line. Datetimes become strings. The loaders (`Theme::load`, `Plugin::load`, `plumblog_i18n::parse`) and the checks that live in them (option schema, locale keys) run on the Worker over the JSON.
- Options: `theme.toml` declares `[options.<key>]` in the shape of "Plugins and options": `type` is one of the admin field types (`short_text`, `long_text`, `number`, `toggle`, `choice`, `color`, `image`, `list`), plus `default`, limits, `group`, `icon` and locale keys for `label`/`help`. Templates read `theme.options.<key>`; a `color` option names the token it overrides. A `choice` option may map each value to a CSS file (a **style**): only the selected file ships after `style.css`. Values listed in `draft` are not offered to owners. Stored values are JSON in `extension_options`, read once per page render (pages are cached by the content version every option write bumps). Declarations are checked at load (types, defaults, limits, groups, label/help keys present in `locales/en.toml`, stray keys rejected); a stored value that fails its declaration (wrong type, out of range, draft choice, non-hex color) is replaced by the default and logged (`option.invalid`), never breaking a page. Value shapes: `image` is a media id or `""`, read in templates as `theme.options.<key>.id` so a resolved URL and size can be added later; `list` is an array of short strings (`max_items`, `max_len`). `blog guide options` prints the schema, generated from the Rust types.
- Templates link optional theme files with `asset("<path in assets/>")`, e.g. a script only some pages load.
- Slots: themes expose named empty points for plugin partials with `{{ slot("<name>") }}`, chosen from `head`, `body_start`, `body_end`, `before_post`, `after_post`, `footer`. A theme lists the slots it offers in `theme.toml` (`slots = [...]`); calling an unlisted slot is a template error.
- Themes may contain JS. Installing a theme not made locally shows a warning.
- **minimal** is built first; literary and technical follow once it is approved.
- Fonts: pick the most readable font for the theme's role that covers Latin (incl. Vietnamese), Cyrillic and Greek; modify (subset) it if needed, within its license. Loading rules:
  - Self-hosted on the blog's own domain, never a font CDN.
  - Split into `unicode-range` subsets (latin, latin-ext, vietnamese, cyrillic, greek) so a page downloads only the scripts it uses. Variable weight axis only, trimmed to the weights used.
  - Preload only the body latin subset. `font-display: swap` with a metric-matched fallback (`size-adjust`, `ascent-override`...) so the swap causes zero layout shift.
  - CJK, Arabic, Thai and other scripts use system fonts.
- minimal uses **Inter** (v4, OFL): high x-height, screen-first, wide language coverage. Body 17px phone to 19px desktop (rem, so user font size still scales), line-height 1.7 (Vietnamese stacked diacritics), measure 32 x font size (~66 characters), near-black on white, off-white on near-black in dark mode, `cv05`/`cv08` to tell I/l/1 apart, balanced headings, no orphan words. Accent: plum.
  - Preload the body, title and mono latin subsets plus the page language's subsets (`preload_by_lang`), so their letters never swap in late and move the layout; mono is above the fold in the writer style (site name, dates), and preloading it keeps mobile Lighthouse at 100.
  - `scripts/subset-fonts` builds the woff2 files and `faces.css` from the pinned official release. Weight axis 400-700 (starting at the default saves ~20% per file, so dark mode softens text by color, not weight); optical size pinned to the text cut. Subsets never overlap, so a Vietnamese page fetches latin + vietnamese only. Fallback face is Arial with metrics matched to Inter.
  - Typography values are CSS custom properties at the top of `style.css`; the editor's writing column reuses them.
  - Renderer contract: color tokens are emitted once as `--c-<key>: light-dark(<light>, <dark>)`, so `color-scheme` (system, toggle, print) switches the palette without a second block; footnotes as `<sup class="fnref"><a href="#fn-N">` plus `<section class="footnotes">` with `<li id="fn-N">` and `a.fnback`; code blocks as `<div class="code" data-lang="rust"><pre><code>` with `tok-keyword|string|number|constant|function|type|builtin|property|attr|tag|punct|operator|comment` spans; wide tables wrapped in `<div class="table">`; task-list items as `<li><label><input type="checkbox" disabled> text</label></li>`; table cell alignment as `data-align` (no `style`, so a strict CSP applies); callouts as `<div class="callout" data-kind="note" role="note">` (the theme supplies any label); embeds as `<div class="embed" data-provider="youtube" data-id="...">` holding a plain link, which theme JS may swap for a click-to-load player; invalid math as `code.math-error`; a `wide` class on a figure lets it bleed to the screen edges on phones.
  - Type scale: five sizes as steps of the body size (`--t-xs` .8125, `--t-sm` .875, body, `--t-md` 1.125, `--t-lg` 1.375, plus `--t-xl` for h1), never em multiples. Mono sits one step below the Inter beside it: same x-height, wider letters. Rows that mix fonts share a baseline.
  - Search: the header magnifier opens a search panel under the header (`/` also opens it, Esc closes); results appear as you type, read from the search page's own HTML, so core needs no second endpoint. Without JS the magnifier is a link to `search.html`, which gets `query` and `results` (post rows) and works as a plain GET form. Shown when `site.search_url` is set.
  - Comments: `post.html` gets `comments` only when comments are on: `open`, `items` (`id`, `author`, `owner`, `date_iso`, `date_display`, sanitized `html`), `action_url`, `turnstile_key`, `max_length`, `more` (older approved comments were left out). The form redirects back with `?comment=pending` or `?comment=error&code=<stable code>`; the theme shows the result with JS, since the HTML is the cached page. Turnstile loads only when the reader focuses the form, into a box whose height is reserved; the draft survives a failed send; without JS a note says sending needs it.
  - Titles use **Inter Display** (Inter's display optical size, one static weight, Latin scripts only; Cyrillic and Greek titles fall back to the text cut).
  - Styles: **writer** (default; text first like a writing app), **book** and **magazine** (drafts, offered once they reach the writer standard). Options: style, accent, list images (off), excerpt words (55), sidenotes (on).
  - writer home: one row per post, pinned first, in a grid with a narrow mono date column that hangs in the left margin on wide screens and moves under the excerpt on phones; title, excerpt, optional small 4:3 picture. Rows are separated by space, not rules.
  - Code and metadata use **JetBrains Mono** (OFL, one weight, no ligatures so readers see what is typed). No uppercase or small caps anywhere.
  - Shared tokens at the top of `style.css`: radii (`--r-sm` 4, `--r-md` 6, `--r-lg` 8), `--tap` 44px, `--ctl-sm`, spacing `--s-1`..`--s-7` (rem), shadows `--raised`, `--pressed`, `--inset`, `--pop`. Controls use only these; spacing inside running text stays in em so it follows the text size.
  - Controls follow the admin design language: one state system (hover, pressed, selected, focus ring, disabled) shared by the toggle, copy button, checkboxes and footnote buttons.
  - Sidenotes move into the margin from 76rem (~1216px) wide; narrower screens, folded or unfolded foldables included, get the inline toggle.
- Footnotes are sidenotes: in the margin beside the sentence on wide screens, an inline toggle under the sentence on narrow screens, classic bottom footnotes when JS is off. About 1 KB JS.
- Commands: `blog theme new <dir>` copies the default theme; `blog theme dev <dir>` previews it on 127.0.0.1 with sample posts (edits show on refresh; problems shown in the page); `blog theme check <dir>` reports template errors, missing dark tokens, contrast failures, size, hard-coded colors and text, and files that must not be public (`.env`, keys, `secret`/`credential` names, token files; `tokens.css` passes), each with file:line and a fix, plus asset names outside `[A-Za-z0-9._-]` per path segment (`file.asset_name`), text files over 4 MiB, any file over 25 MiB (`file.too_large`), non-UTF-8 files outside `assets/` (`file.not_text`), a `theme.json` over its budget (`theme.too_large`), and files the theme uses but lacks in its `assets/` (`theme.asset_missing`: `asset("...")` in its own templates and the default templates it borrows, `url()` in its `assets/` stylesheets, `{{fonts}}` files, `theme.toml` preload and script paths); the secret scan reads every file a push would ship, whatever its size or encoding (non-UTF-8 bytes as lossy UTF-8); `blog theme dev` serves only the folder's own `assets/` (no default theme behind it, no symbolic link on the way, resolved path inside `assets/`), as the Worker does; `blog plugin check <dir>` does the same for a plugin on the default theme. `blog theme push <dir>` (holds `.blog-deploy.lock`) runs the check and refuses on any error before any call, then makes a new Worker version through deploy's own path (same bundle resolution `--bundle`/`--build`, assets upload with the theme files added under `_theme/<name>/`, same bindings plus `PLUMBLOG_THEME`, smoke check, rollback on failure, a deploy record with `kind = "theme_push"` and `theme = {name, version, hash}`); no migration, export or bookmark: a bundle with pending migrations is refused (`theme.push_pending_migrations`, run `blog deploy` first). `blog theme push --default` makes a version without the binding and `_theme/` files (`kind = "theme_default"`). `blog theme rollback [--to <version-id>]` goes back to the version before the newest serving theme push, or to a version a recorded theme push made, through `blog rollback`'s path and guards (placeholder, `rollback.older`), and prints the theme that now serves; `blog theme list` prints the records with their themes. Theme files are public: no secrets.
- Pushed themes: binding `PLUMBLOG_THEME` names the active theme; its text files are one static asset `/_theme/<name>/theme.json` (`{api, name, version, hash, files, assets}`, `plumblog_render::PushedTheme`, `THEME_API` = 2: the first released format; its TOML files are the converted `.json` keys above and the document holds no TOML text), other assets (the folder's `assets/`) under `/_theme/<name>/assets/`, each listed in `assets` with its SHA-256. `hash` is the SHA-256 of `PushedTheme::hash_input` (text files and the asset list, length-prefixed, in path order). The Worker fetches it once per isolate through `ASSETS`, loads it with the embedded default as fallback for missing templates and locales, and on any failure renders the embedded default and logs `theme.pushed_missing` / `theme.pushed_invalid` once per isolate (`theme.pushed_fetch_failed` is retried). Page cache keys and ETags carry `-t<hash[..16]>`, and pages it rendered send `x-plumblog-theme: <hash[..16]>` (`pushed::THEME_HEADER`; absent when the default rendered). The smoke check of every new version (`blog deploy`, `blog theme push`, `--default`) requires `/` to send the tag of the theme on its deploy record, or no tag for the default; anything else fails the check and rolls back (`blog rollback` does not check the theme). A page the pushed theme's templates fail to render (an error only real data shows) is rendered again with the embedded default, served uncached without the tag, and logged (`theme.pushed_render_failed`, with the path); storage errors are not theme errors and take the plain 500 path (`pages::RenderError`). Each kind of theme log line (missing, invalid, too large, fetch failed, render failed) is written once per isolate, so one never hides another. While `PLUMBLOG_THEME` names a theme that did not load, writes to its options are refused (409 `theme.unavailable`), since its declarations are unknown. A later deploy fetches assets back by `pushed::asset_url` (each path segment percent-encoded). Option writes are checked against the active theme's (or bundled plugin's) declaration: a failing value is 400 `input.invalid` (field `value`); undeclared keys are kept. Binding `PLUMBLOG_THEME_TAG` (plain_text) is the first 16 hex characters of that `theme.json` `hash`, for `blog deploy` to set wherever it sets `PLUMBLOG_THEME` (not written yet: until it is, pushed-theme hits go through wasm); the JS entry (Worker entry decision, 2026-11-28) needs it to build the cache key, and delegates to wasm without it.
- A theme survives later deploys: every version uploads all its static files, so `blog deploy` reads the serving version's `PLUMBLOG_THEME` (`GET .../versions/<id>`) and uploads the same theme again: from the local copy `.blog/themes/<hash>/` (git-ignored, written by each push, newest 5 kept) when the serving version's deploy record names that hash and the copy verifies, else fetched from the site (public, no token; from its workers.dev address when it has a custom domain, whose cache rules could serve an old copy, with `Cache-Control: no-cache` and a `fresh=` query on every file) and verified file by file against `theme.json`. A theme that cannot be recovered refuses the deploy (`deploy.theme_unrecoverable`): push the folder again, or `blog deploy --theme-default` to drop it on purpose.
- The template variable reference is generated from Rust types, never written by hand.
- Owner-only admin page for colors, fonts, logo.

## Plugins and options

- Themes and plugins declare options; they never ship admin UI. A declaration lists fields from a fixed set of types owned by the admin (short text, long text, number, toggle, single choice, color, image, list), with labels and help as locale keys, grouping, and icons by name from the admin icon set. The admin renders every field with its own components, so every theme and plugin tab follows the admin design language.
- Settings: **Appearance** shows the active theme's options; **Plugins** lists plugins (enable/disable) with one tab per plugin, generated from its declaration.
- Plugins are declarative only: settings, HTML partials for named slots that themes must expose (head, body end, before/after post, footer...), browser JS/CSS, locale files. No server code inside the blog. A disabled plugin costs zero bytes.
- Plugin folder `plugins/<name>/` (name: lowercase letters, digits and `-`, equal to the folder): `plugin.toml` (`name`, `version`, `slots`, `css`, `js`, `[groups.*]`, `[options.*]` in the theme schema), `partials/<slot>.html` for each declared slot, `assets/` (served at `/plugin/<name>/`), `locales/<lang>.toml`. Any other file, an asset path outside `assets/`, or an undeclared partial fails the load.
- Partials are minijinja templates in the theme's sandbox, autoescaped; they see `site`, `page`, `plugin.name`, `plugin.options` and `t()` over the plugin's own locales. They only fill slots: `extends`, `block`, `include`, `import` and `from` are rejected. A slot renders every enabled plugin's partial in plugin-name order; a partial for a slot the theme does not offer is not shown and logged once per render (`plugin.slot_missing`), not an error.
- Plugin CSS is inlined after the theme's and plugin JS loads deferred, only when enabled. Several enabled plugins may push the page over the CSS budget (served anyway; the admin will warn); `scripts/check` fails for any bundled plugin that alone takes the default theme over it.
- Plugins come only from `plugins/`, embedded at build; their enabled state is the `plugins` table, disabled by default. Uploading plugins comes later.
- A plugin that fails to load, or a partial that fails to render, is left out of the page and logged (`plugin.broken`); reader pages never write, so the automatic disable and naming it in the admin happen in the admin and `blog plugin check`.
- Complex needs are the user's own project: a separate Worker or service talking to plumblog through the API and outgoing webhooks (post published/updated/deleted). Core adds webhooks, nothing more.
- Isolation: no theme or plugin HTML, CSS or JS ever runs in the admin. Theme CSS needed in the admin (editor typography, live preview) loads in an isolated frame. Admin has a strict CSP. `blog theme check` and `blog plugin check` reject unknown field types, hard-coded text and admin-targeted files.
- A broken plugin is disabled automatically and named in the admin; the blog keeps working.

## Admin and editor

- Markdown source editor (CodeMirror 6) with live styling: syntax marks dimmed, headings and emphasis styled as typed. Modes: Write / Split / Preview (tabs on mobile).
- The writing column uses the active theme's font and line-height, so writing looks like the result, at a calmer size (see Design language).
- Toolbar that fades while typing; selection bubble (bold, italic, link); `/` menu for blocks.
- Paste or drop images: placeholder with progress, encode, insert, ask for alt text. Paste from Word/Google Docs converts to Markdown. Pasting a URL over a selection makes a link.
- Focus mode, typewriter scrolling, word count, discreet "Saved", offline draft in IndexedDB, drafts saved to the server as you write.
- Post settings in a collapsible side panel. Publish button always in the same place.
- Publishing (`web/admin/src/editor/publish.ts`, its own lazy chunk): the button at the top right reads Publish, Update (live post) or Schedule (later is picked) and opens a confirm with the address, the time and the length. Confirm sends ONE update: the editor's text, `status`, `published_at` (only for later, or to replace a scheduled time with now) and the slug if it changed, conditional on the version sync holds; a new post is created first by sync's own path, never twice. A stale version opens the same choice banner as autosave; a taken slug opens the slug field. The settings panel (slug, now or later, unpublish, trash) uses the same update; unpublish sends `status: draft` and `published_at: null`. A live post's edits stay on this device until Update; autosave runs only while the post is a draft.
- Admin in light and dark; English and Vietnamese UI.
- Posts list (`web/admin/src/lists.ts`): All, Draft, Scheduled, Published, Trash, kept in `?status=` (no counts, no search). The API cannot leave a status out, so All asks without `status`, drops trashed rows and keeps loading pages until 20 rows show (at most 5 extra requests, then "Load more"). Above it, with All, a strip of up to 3 drafts that exist only in this browser (IndexedDB, not saved to the server yet). Pages: the same list with no filter.
- Dashboard (drafts, recent posts, last backup time), media library, users/invites, settings, tokens, audit log, update notice from GitHub Releases.

How the admin is built:
- No framework: TypeScript ES modules in `web/admin/src` with a small own DOM helper (`dom.ts`); screens are forms and lists, and CodeMirror owns the only complex DOM. `tsc --noEmit` type-checks, esbuild bundles and code-splits (shell; editor and image encoder load on demand). Pinned in `tools/package.json`, which says why for each tool.
- Built by `scripts/admin-build` into `target/admin` (the mock build into `target/admin-dev`) and never committed: `scripts/check` builds it once, worker-test serves it from `target/worker-test` (`scripts/admin-dev` from `target/worker-dev`, so a check never swaps files under it), and releases ship it prebuilt like the Worker wasm (#21), so owners never need Node. The build writes `_headers` for Workers static assets: hashed chunks `immutable` for a year, `app.js`, `app.css` and `sw.js` revalidated; the release must put it at the assets root.
- Served as Workers static assets under `/admin/`; every other `/admin/*` path gets one HTML shell from the Worker (`crates/worker/src/admin.rs`) naming one language (cookie `pb_lang`, else `Accept-Language`, else the site language) and preloading that language's UI text module, `/admin/i18n/<lang>.js` with English behind it, and `modulepreload`ing every static chunk of `app.js`, so the shell's scripts load in one round trip, not one import level at a time (admin-build writes the list from esbuild's metafile to `target/admin.preload`; the Worker's `build.rs` embeds it, so the admin is built before the Worker that ships with it, and a plain `cargo test` build has an empty list; worker-test compares the served links with the metafile). The writing faces are preloaded only on the editor and sign-in pages, the ones that set text in them: on the posts list they delayed the LCP row text by 0.6 s in mobile Lighthouse. The text is part of the admin build (`crates/i18n` `admin`, run by admin-build), not the Worker: the wasm embeds only the bare `[admin]` section (title, noscript), so admin screens never grow it. Strict CSP: scripts and styles from the site only, no inline code; the client sets styles through the CSSOM. The one style exception is CodeMirror's base-theme `<style>` element, admitted by a per-response nonce (sent in the boot JSON); style attributes stay blocked. One script exception, per route: `/admin/signin`, `/admin/setup`, `/admin/invite` and `/admin/reset` add `https://challenges.cloudflare.com` to `script-src` and `frame-src` for Turnstile, whose script is injected only after the server answers `auth.turnstile_required`. A Turnstile token never sends a request by itself (the widget may solve itself, also after a reset): each writer submit sends at most one, with an unused token, and the widget is reset only for a submit that needs a new one. The client reads a path with at most one trailing slash, as the Worker and the service worker do. The client reaches those pages only by a full page load (a session that ends mid-edit goes to `/admin/signin?next=<page>`; the draft is in IndexedDB), so no other page ever runs under that policy, and the service worker never caches them as the offline shell. `next` is followed only when it is a path under `/admin/` (no `//`, backslashes, encoded slashes or absolute URLs). The auth pages pick their language as cookie, then a stored `site_lang`, then `Accept-Language`, so a fresh site's owner sees the site's language before any account exists, and they carry an en/vi switch. Sign-in on a site with no owner yet (`setup_required` in `/api/auth/params`) moves to `/admin/setup`. Signed-in pages never load Turnstile: on the account page (passkeys, for every role), a re-auth answered with `auth.turnstile_required` reads like a lock (wait out the 15-minute window). The account page fetches its chunk and its two lists (passkeys, API tokens) beside `me` (`early.ts`), shows the tokens section only once the passkeys list has its height (no layout shift), and is not redrawn on a network change, only its offline banner follows, so a token shown once survives a blip. Signing out asks first when this browser holds drafts of that user, which it then deletes; a failed sign-out deletes nothing.
- Installable: the Worker serves `/admin/manifest.webmanifest` (scope `/admin/`, "<Site> admin") and a default icon (the site's first letter on a signal disc, on a dark plate) until a site icon can be uploaded. A service worker keeps the shell offline, network first; it never caches `/api/`. Its cache is named after the build's hash and holds only the shell and that build's files (listed at build time); activating a new build deletes the old cache. A missing `/admin/` file (an extension or under `chunks/`) is a 404, never the shell.
- One API client (`web/admin/src/api/client.ts`): every call resolves to a result with the server's stable error code, never throws, and logs failures. Codes, roles, permissions and the post types are generated from `crates/model` (`model.gen.ts`, kept current by a test; the post shapes come from `crates/model/src/shape.rs`); other API body types join them as they move into `model`. `api/mock.ts` implements the same interface over `web/admin/fixtures` so screens are built before their API (`scripts/admin-dev`, with `?mock=loading|error|offline|empty` and `?role=writer`; fixtures may hold non-ASCII text so the mock shows real Vietnamese); admin-test checks the fixtures and the mock's answers, and worker-test the fixtures and the real API's answers, against the generated `SHAPES` table with one shared checker (`tools/shape-check.mjs`), so mock and Worker cannot drift apart.
- Preview: the Worker renders the draft with the site's theme and options (debounced form POST into a frame), so it is the published page; offline, it says so. The frame is sandboxed without scripts and the Worker drops `<script>` elements from it, so no theme code runs; it keeps the admin's origin only so theme fonts load. The response itself sends `content-security-policy: sandbox allow-same-origin; script-src 'none'; frame-ancestors 'self'`, so it stays script-free when opened on its own and only the admin can frame it (`allow-same-origin` because an opaque origin fails the fonts' CORS check). Each refresh posts into a new hidden frame that replaces the shown one when loaded, so previews add no history entries. The cost: client-side theme features (code highlighting in the default theme) do not show in the preview. Route: `/api/preview` with the posts API (#10); until then the mock posts to the test-only `/__preview`, which reports its render time in `Server-Timing`.
- Editor (`web/admin/src/editor/`): CodeMirror 6 with the Markdown language only (not `markdown()`, whose embedded HTML/CSS/JS parsers do not fit the chunk budget) and the standard keymap, not the code-editor one; every change is kept first in IndexedDB, keyed per user and post (`<user>:post-<id>`, or `<user>:new-<id>` with the id in the URL, so new posts never share one) and cleared at sign-out; every save is conditional on the draft's revision, checked and written in one transaction, so a second tab pauses and asks instead of overwriting; a page writes only the draft and its own side copy (`<key>~<tab>`, new per page load): typing while paused goes there, and so do keys typed within the 700 ms debounce when the tab is hidden or closed (then the usual save; the copy goes once its text is in the draft). Another page's copy is never written or taken in silently: on open, one equal to the draft is removed and every other is offered in the tab choice, newest first and one after another, each removed only after its pick; the posts list and the sign-out count show one entry per post. An expired session saves the pending keys before going to sign-in (bounded wait). A draft (or new) post is also sent to the server (`editor/sync.ts`, its own lazy chunk) about 3 s after the last local save, while online, one request at a time: the first save creates the post (slug from the title, `-2`... on a taken one; an editor redrawn meanwhile, by online/offline, waits for that create and opens the post; a reload while it is out is asked about first), moves the draft to `<user>:post-<id>` in one transaction (the new-post key keeps only a dated note of where it went, swept after a day: opening that key, or a save to it from a page still open on it, moves any copy left there along and opens the post, never creating it twice) and replaces the URL; every update names the `version` the text is based on, and the local draft is dropped once the server holds exactly the editor's text at an unchanged revision. Published and scheduled posts are never sent from the editor (only the publish step changes the live page) and stay on this device; the same holds for good once any server copy the editor sees (a 409's fetch, any answer) is no longer a draft, so "Keep my draft" then keeps it on this device only. A request with no answer in 20 s fails as `network` (the draft stays; the next change retries). The API client sets no bound on a create; sync does: every create of one new post sends one `client_id` (a UUID kept in localStorage under the draft key until a create answers with a post or refuses the body (a 4xx other than 401, 403 and 429), so a reload sends it again), and one with no answer (network error, or none in 20 s, the first left out) is sent again 4 times, 1, 2, 4 and 8 s apart; the server answers each with the same post. A create out for 20 s (retries included) says so on the status line until one lands. A post answered with older text than the create sent (an earlier attempt's) gets the editor's text as an update, unless it was edited since (version above 1, other text): then the writer picks, as on a 409, and the draft stays based on version 1 so a reload asks too. A 409 whose server copy is exactly one of this editor's updates that got no answer since the last answered one (up to 20 kept), typed on since, is its own save: the newer text goes on that version, no choice. Without localStorage a reload after a lost answer can still leave a second server draft, never lost text. Publish, Update and Unpublish hold autosave from the create they may need to their answer, so no autosave carries the same `version`; their 409 adopts the server's status first (a post published elsewhere stops autosave before the writer picks). A trashed post opens in a trashed state: nothing is sent (the server refuses edits), Publish is off and the panel offers no Trash; its banner's Restore brings the post back with its old status, and a draft's autosave then resumes. Trash holds autosave like a publish step, and the panel's Unpublish and Trash are off while a step is out; a step stopped by a text choice tells the writer to press it again. A draft's slug follows a retitle while it still matches the title it was made with (autosave does not count); the address the confirm shows is the slug sent. A draft stores the server `version` (and `updated_at`) it started from; when the server copy has moved on, at load or as a 409 on save, saving stops and the writer picks which text to keep. Nothing is picked silently. A picture alone on its line shows as the picture and its caption; its source appears while the caret is on that line. The writing column uses the default theme's Inter, Inter Display and JetBrains Mono, copied into the admin build (never loaded from the theme) with `font-display: optional`, the main faces preloaded by the shell and precached by the service worker, so a late font is skipped rather than reflowing the text; a picture sits in a fixed 3:2 frame known before it loads, so nothing moves when it arrives; the active theme's font follows with the theme settings API. On touch screens there is no selection bubble: the bottom bar acts on the selection. Pasting: HTML with structure (Word, Google Docs, web pages) becomes Markdown in the browser (headings one level down, since the title is the only top heading; Word's `mso-list` paragraphs become lists; links lose Google and Outlook redirects; only `http(s)` pictures travel), by a small module loaded on the first such paste; inside code, and for plain HTML, the plain text is pasted. An address pasted over selected words links them. Pictures (paste, drop, the toolbar or `/` menu) upload one by one through the API client's `upload`, each as a card with progress under its line that moves with the text; on success its Markdown takes the card's place and the writer is asked for a description (skippable; the caption then flags it); on failure the card says so and offers another try or removal, and the text is never touched. Offline, non-pictures and files over 20 MB are refused with a message. In-browser AVIF encoding before upload comes with the media API.
- UI text: `t("literal")` only, `[admin.*]` keys in `locales/`; a key built at runtime is a template string with `// i18n: <every key>` above, checked by the locale test like templates. The test also rejects text that bypasses `t`: string literals with letters as `h()` children or `aria-label`/`title`/`placeholder`/`alt` values, and `t` imported under another name.

### Design language

Models: Bear and iA Writer for focus; Braun and Dieter Rams (Bauhaus) for the controls. Everything serves writing; the chrome is quiet and practical, and every control reads as a physical key you can press.

- **Type.** UI: system font. Scale 11 / 12 / 13 / 14 / 16 / 20 px, weights 400 / 500 / 600 only. Labels and metadata 12-13 px; section labels are 12 px, weight 600, muted, in normal case. No uppercase or small caps anywhere (scripts/check enforces it). Numbers, sizes and dates use tabular figures; file names use the mono font at 12 px. Writing column: the active theme's font and line-height, at a calmer size than the reader page (16 px phone, 17 px desktop, line-height 1.65, max 64ch); title 1.5em, weight 650.
- **Space.** 4 / 8 / 12 / 16 / 24 / 32 / 48 px. Rows are dense (list row 56-64 px) and separated by spacing and a soft hover or selected surface, never by full-width rules; whitespace goes around the writing column, not inside controls.
- **Color.** Off-white and warm greys, never pure grey; ink (near-black, near-white in dark) for primary actions. One accent, Braun signal orange (light `#c4561f`, dark `#e0804b`), only for caret, selection, links, the focus ring and lit lamps (a switch that is on, a latched key). Status colors are muted, Pantone-like: draft = warm grey, scheduled = ochre, published = sage, error = brick; text on a status tint keeps 4.5:1.
- **Shape.** Generous rounding: buttons, segmented controls, tags, status chips, toasts and the editor toolbar are pills; icon buttons, switch knobs, radios, lamps and status dots are circles; fields 10 px, menu items and nav items 9-10 px, list rows 12 px (0 on phones), popovers 14 px, checkboxes 6 px.
- **Depth, kept shallow.** Keys: a key face (`--key`) with a lit top edge and a 1-2 px cast shadow (`--sh-rest`). Wells: text fields, selects, switch slots and segmented tracks sit slightly recessed (`--well`, `--sh-well`). Raised and sunk must read at a glance but never look deep or heavy. Popovers, the floating toolbar and the phone bar cast a soft shadow; nothing else does. No gradients on control faces.
- **States, one system for every control.** rest = raised key (quiet icon buttons are flat until hovered); hover = the key lifts (bigger shadow, 1 px up), flat items get a 6% ink tint; pressed = the key sinks (inner shadow, 1 px down, darker well color); selected = the key stays latched down and its lamp lights in signal orange, while a selected flat item (nav, menu, row) becomes a raised key outlined on all four edges; focus-visible = 2 px signal ring outside a 2 px gap, never removed; disabled = 40% opacity, no shadow, no motion. Transitions 120 ms ease-out.
- **Icons.** One line set, 1.5 px stroke, round caps and joins, 16 px in lists and sidebars, 20 px in the editor toolbar; icon-only buttons are round, 32 px (36 px in the editor toolbar, 44 px on touch), with a tooltip and an accessible label. The editor toolbar is a contained pill centered on the writing column, never an edge-to-edge strip; what does not fit goes into an overflow menu.
- **Layout.** Page header 60 px, its middle level with the logo in the sidebar. Title left; actions right; search, where a page has it, is always the rightmost control, so it sits in the same place on every page. The account entry is an icon with name and role, no avatar. On phones the navigation (posts, pages, media, settings, account) is a floating glass pill above the bottom edge; the current item is a lighter lens with a signal-orange icon and label.
- **Media.** A grid of pictures with name and size below; a missing description shows as a lamp badge on the picture. Each picture has an eye button (on hover, always on touch) that opens a full-screen dark viewer with previous/next, arrows and Esc, and focus returns to the picture. Details sit in a card: the picture at its true proportions, then description, where it is used (links to posts), file size and actions. Filters: all, no description, unused.
- **Color swatches.** Flat discs of color with a 1 px rim and no shading; hover adds an outer line ring, the selected disc gets a 2 px ink ring outside a 2 px gap, focus the signal ring.
- **One stylesheet system.** `web/admin/css/tokens.css` holds every raw value: colors per theme, type roles, the space scale, control sizes (32 px, 44 px on touch), radii, shadows, durations, z-index. `components.css` defines each shared piece once: buttons, fields, switches, segmented controls, nav items, page header, filter row, list rows, sections, empty and loading states, popovers, toasts, the drawer, the toolbar, the viewer. Page files (`pages/*.css`) only lay out and compose; a page that needs a variant adds a modifier to the component. `scripts/check-admin-css` enforces it: no raw value outside tokens, no component restyled in a page file. Every screen is checked at 344, 375, 673, 768, 884 and 1440 px, light and dark, English and Vietnamese, including empty, long text, loading, error, offline and writer cases: no overflow or misaligned edges, text contrast 4.5:1, touch targets 44 px, a visible focus ring on every control.
- **Motion.** 120 ms for states, 180 ms for panels and popovers (opacity + 4 px translate), nothing while typing except the toolbar fade. Off under `prefers-reduced-motion`.
- **Never:** big rounded cards; soft drop shadows on everything; gradients on controls or swatches; glass except on the phone bar and on buttons over pictures; emoji or filled cartoon icons; everything centered; oversized hero text; colored icon tiles; decorative illustrations; more than one accent; status shown by color alone; uppercase or small-caps text; full-width rules between list rows; edge-to-edge toolbars.

## AI surface

- `blog` CLI: setup, deploy, and primitives (posts, media, settings, themes, tokens).
- HTTP API with generated reference.
- API tokens (issue #10): `plb_` + 32 random bytes in base64url, shown once at creation; only the SHA-256 hex of the full text is stored. A name (1-64 characters, no control characters) and an optional expiry (UTC ms, sent as a decimal string; default none). Scopes `read` < `writer` < `owner`; `read` reads everything a signed-in user can (drafts included) and writes nothing, the suggested scope for an agent that only looks. A token's scope cannot exceed its creator's role, and it acts with min(scope, the user's current role): a demoted owner's owner token acts as writer, a disabled user's tokens answer 401 (disabling revokes them), revoking is immediate. Resolving a token reads the token and the user, and writes nothing (no last-used time).
- `Authorization` means a token and only a token: a malformed header (anything but `Bearer plb_<43 base64url>`, scheme in any case) is 401 `auth.unauthenticated`; the request skips the `Origin` check (a browser never sends the header on its own and there is no CORS) and the cookie is ignored entirely (not read, renewed or cleared). `/api/auth/*` is session only: tokens get 403 `auth.forbidden` there, so a leaked token cannot mint tokens, change the password, add a passkey or end sessions. `POST /api/auth/tokens` (201 with the token), `GET /api/auth/tokens` (own tokens, never the secret or hash), `DELETE /api/auth/tokens/<id>` (own only; another user's is 404). Writes through the API record `via` = `session` or `token` and, for a token, `client` = its name and id (a separate field: "token <name>" in one value would be redacted as a secret); the redactor also knows the `plb_` prefix.
- Migration 0005 rebuilds `api_tokens` to allow `read` (SQLite cannot change a CHECK in place): copy every row with its id into a new table, drop, rename, recreate the index; nothing references the table. `migrations.test.mjs` proves every 0001/0002 sample row comes through unchanged and that the rebuilt table keeps its constraints.
- `/api/v1` (issue #10): one route table in `crates/model/src/api.rs` (method, path, access, fields with type, place and required, body cap, status, response shape name) drives the Worker's router (an exhaustive match, so a route without a handler does not compile), `GET /api/v1/reference` (JSON) and `blog guide api`; nothing is written by hand. Session or token alike; `read` covers every GET, drafts and trash included. Input is checked against the table before a handler runs: unknown, duplicate, missing or mistyped fields (query, path, body) are 400 `input.invalid` with `field`. Bodies are strict JSON (`plumblog_auth::json::parse_document`): integers only in the i64 range (no fraction, exponent or leading zero), nesting <= 16, <= 1000 items per container, keys <= 64 bytes, <= 4096 values in all (members plus items at every depth; past it 413 `input.too_complex`; the largest real body, a post with 1000 tags, holds 1015, `crates/auth/tests/value_cap.rs`), duplicate keys found by sorting keyed hashes (O(n log n); a large object reports its duplicate when it closes); `crates/auth/tests/perf.rs` holds every 160 KiB body, accepted or refused, under 1 ms natively (22 objects of 1000 keys took ~1.2 ms here, ~3 ms on CI, before the value cap); `clientDataJSON` and `/api/auth` keep the flat string/boolean reader. Lists are keyset-paged with an opaque base64url `cursor` and `limit` <= 100 (default 20), `next_cursor` null on the last page; tags and series page by slug (unique, so the slug alone is the keyset; the cursor is the base64url of the last slug; `crates/worker/src/d1/reader_sql.rs` checks both plans), the store looking one row past the page itself. `GET /api/v1/posts` also answers `counts` (posts per status, trash included) on the first page only (`null` with a `cursor`); it follows `kind` and `lang`, not `status`, `tag`, `series` or `author`, and is one covering scan of `posts_listing`.
- Post saves render Markdown on the server (`plumblog_markdown::render`, default options) and derive, from the HTML, the search text, the word count (`plumblog_markdown::word_count`, the reading-time counter: each CJK or Thai-like character is a word) and the body media for `post_media`: `<img src>` of the form `/media/<id>` followed by `/`, `.` or the end (`/media/12/heron.avif`, `/media/12.avif`); media answers carry `src` = `/media/<id>/<file name>`. `PATCH` changes only the fields sent and needs `expected_version`; a stale one is 409 `{"error":"store.conflict","field":"expected_version","version":<current>}`, unless the stored post already holds exactly what this update would write (every column the save sets, tags as a set; `SavePost::matches`): then it is the same update again, its answer lost, and the answer is 200 with the stored post, nothing written or logged. A taken `(lang, slug)` is 409 on `slug`. `POST` takes an optional `client_id` (1-64 of `A-Z a-z 0-9 - _`, else 400 on `client_id`; a body field, not an `Idempotency-Key` header, so the route table checks and documents it like every other input): a key this user already created a post with answers 201 with that post as stored now, whatever the body says, and writes and logs nothing (the client may have edited since; its next PATCH carries that). Stored with the post (`posts.client_id`, migration 0008), unique per `(author_id, client_id)`, so it lasts as long as the post (a permanently deleted post frees its key) and needs no TTL; a create with a key costs one lookup query first; two creates with one key at once make one post (the index refuses the second insert, which then reads and answers the first; the store reports it wrote nothing, so only the winner logs `post.create`). A sign-in refusal (401, 403, 429) is checked before the lookup, so the editor keeps the key through it. Keys are per author: another user's same key is a new post. Without new Markdown the stored rendering stays; a written excerpt stays until replaced, `""` or a new body without one takes the automatic excerpt. Status `draft | scheduled | published` (trash has its own routes; delete only from the trash); publishing without `published_at` uses now, scheduling needs a future time. Another author's post needs `post.edit_any` (`post.delete_any` to trash or delete); making or keeping a post live needs `post.publish`. Every write logs `content.changed` with `action` (`post.create`, `tag.update`...), the id, `via` and `client`.
- Media (`/api/v1/media`, `media.upload` for writes; upload and alt-text edits by any writer on any item, the library is shared; deleting needs the caller's own upload, else `media.delete_any` (owner), which an item whose uploader was deleted (`uploaded_by` null) needs too): the upload body is the original image itself (route `body: original`, `variants: admin_encoder`: the API stores no AVIF sizes, the admin encoder of issue #13 adds them), metadata in the query (`name`, `mime`, `width`, `height`, optional `alt`). Cap 20 MiB, refused by `Content-Length` (413) before the principal is even resolved, and read only after the route's access check, so an anonymous or read-only caller never makes the Worker take the body in; Cloudflare's request-body limit is 100 MB on Free and Pro (developers.cloudflare.com/workers/platform/limits, Request limits), and the whole body sits in the 128 MB isolate once. Types: AVIF, WebP, JPEG, PNG, GIF; the magic bytes must be the declared `mime`, and `width` x `height` what the header declares (PNG IHDR, GIF screen, JPEG first SOF, WebP VP8/VP8L/VP8X, AVIF any `ispe` box within 256 KiB; JPEG and AVIF may also match turned a quarter, for EXIF orientation and `irot`). R2 key `media/<22 base64url chars of 128 random bits>/<file name folded to a-z0-9._->`. R2 and D1 share no transaction, so the order leaves at worst an unreferenced object, never a row without bytes: upload puts the object, then the row, deleting the object if the row fails; delete removes the row, then the object. An object left behind is logged (`console_error` with its key) and the delete's log entry says `media.delete_r2_left`. Dedupe (issue #60): the client may send `sha256`, the lowercase hex SHA-256 of the body (64 characters, else 400 on `sha256`); the Worker never hashes the body (see Budgets) but hands the hash to R2's put, which refuses bytes that do not match it (400 on `sha256`, nothing stored). The exact rule: a `sha256` that matches one of the caller's own items returns that item unchanged with 200 and writes nothing (one indexed read, `media_uploader_sha256`), without the bytes being checked; a wrong hash is 400 only when it matches none of the caller's items, so a client must send the hash of the bytes it sends (a wrong one can only ever return the caller's own item). Re-uploading identical bytes is therefore 200 with the first item; a new alt goes through PATCH; another uploader's identical bytes make their own item; an upload without `sha256`, and every row stored before migration 0007, is never deduped. Two identical uploads at once: the unique index on `(uploaded_by, sha256)` lets one row in; the other request deletes its R2 object (logged if that fails) and answers the winner with 200. The route table says so (`dedupe: uploader_sha256`, status 200). Deleting media in use is 409 `{"error":"store.conflict","posts":[ids]}`, checked inside the store's delete; ownership is checked before it in the handler (a missing item stays 404), so a refused caller gets 403 `auth.forbidden` and learns nothing about usage.
- Export reads (issue #79, for `guides/export.md`): `GET /api/v1/media/{id}/original` (`read`, like drafts and the media list) answers the stored bytes, not JSON (route `response: original`, `api::ORIGINAL`): the R2 body is handed to the runtime as a stream (`Reply::raw`), never copied through Wasm memory, with `Content-Type` = the row's `mime`, `Content-Length`, `Cache-Control: private, no-store`, `nosniff` and `Content-Security-Policy: sandbox`; a row whose `mime` is not an accepted image type (`MEDIA_MIMES`), an object whose size is not the row's `bytes` or is over `MAX_MEDIA_BODY` is 500 `store.failed` (logged), so nothing active is ever served from the site origin, a row without its object 404 `store.not_found` (logged with the key). `GET /api/v1/comments` (`comment.moderate`: every status, spam and trash included) and `GET /api/v1/users` (`user.manage`, owner only) are keyset-paged by id alone (cursor = the last id), one primary-key range each (`reader_sql` plan test), with no status filter, so a spam flood costs only the page's rows. Users answer named fields only (shape `user`): never a password hash, session, passkey or token.
- Redirects (`settings.manage`): `PUT /api/v1/redirects` `{from, to}`, `DELETE ?from=`; both paths start with one `/` and hold no backslash, whitespace or control character, so a redirect cannot point off the site (`//host`, `/\host`). Settings (`settings.manage`), theme options (`theme.manage`), plugin options and state (`plugin.manage`): values are any JSON, stored as re-serialised from the strict parse. `store::INTERNAL_SETTING_KEYS` are filtered from `GET /api/v1/settings` and refused on write like a bad key (`input.invalid` on `key`); `site_id` is read-only too, as every password's browser salt holds it. `origin` must pass the sign-in code's own parser (`api::site`), so a stored origin always loads. Theme and plugin names and option keys are checked by shape (`a-z0-9_-`, 1-64, letter first), not against the installed theme or bundled plugins; options of anything not installed are stored and never read. Reads of all of these are open to any signed-in caller (`read` covers every GET), except plugin options.
- `origin` and `turnstile_site_key` are session only (`api::SESSION_ONLY_SETTINGS`, listed as `session_only_keys` in the reference): a token setting or clearing one gets 403 `auth.forbidden`, since a wrong origin breaks browser writes and passkeys like the `/api/auth` routes tokens may not use, and a leaked owner token must not turn Turnstile off. Any future setting that weakens sign-in or comment protection joins this list.
- Plugin options are owner only (`plugin.manage`) to read as to write, as a plugin may keep secrets there; theme options stay readable by any signed-in caller.
- Option declarations (the admin's generated Appearance and plugin tabs): `GET /api/v1/themes` lists the installed themes, the embedded default and the theme `PLUMBLOG_THEME` binds (`{name, version, active, source: embedded|pushed, available}`; a bound theme that did not load is `available: false` and the default is active). `GET /api/v1/themes/{name}/declarations` (`read`, like theme option values) and `GET /api/v1/plugins/{name}/declarations` (`plugin.manage`, like plugin option values) answer `option_declarations`, serialised from `plumblog_render`'s own declaration types out of the theme loaded once per isolate: every key present (`null` when it does not apply), the checked default, the limits the write check applies, offered choices only, locale keys as `*_key` beside their text. Text is in `?lang=` (exact, then primary subtag, else English, named in `lang`) from the theme's or plugin's own locales, English behind each missing key; no `Accept-Language`, so HTTP and MCP answer alike. Unknown name: 404 `store.not_found`; a bound pushed theme that did not load: 409 `theme.unavailable`.
- MCP (issue #14: an AI client connects with `https://<site>/mcp` and a token, no clone; `crates/worker/src/api/mcp`): `POST /mcp`, Streamable HTTP, stateless, one JSON-RPC 2.0 message per POST, always answered with plain JSON (never SSE); `GET`/`DELETE` are 405 with `Allow: POST`, no `Mcp-Session-Id`. Why: nothing we serve streams or pushes, and a Worker keeps no state between requests, so sessions and SSE would be code with nothing to carry. Versions 2025-11-25, 2025-06-18 and 2025-03-26; `initialize` answers the requested one when spoken, else the newest; an unknown `MCP-Protocol-Version` header is 400. It shares the `/api/` gate's request id, logging and body refusal (411, 413 by `Content-Length` before reading; cap `MCP_MAX_BODY` = the post cap + 4 KiB of envelope), and parses with the same strict JSON reader (a batch array is -32600, bad JSON -32700, past the value cap 413 `input.too_complex`). Auth is `Authorization: Bearer plb_...` only: no header is 401 before anything else, and a wrong, expired or revoked token or a disabled user's is 401 too, notifications included (the token is checked before the message is read); every 401 carries `WWW-Authenticate: Bearer` with no `resource_metadata`, since there is no OAuth server. The cookie is never read, so there is no ambient credential and no CSRF surface. `Origin` (DNS rebinding: a page on `evil.example` whose name resolves to 127.0.0.1 or a proxy, so its `Origin` and `Host` agree): no header is fine (not a browser); with the `origin` setting, only that origin; without it, only a loopback origin (`localhost`, 127.0.0.0/8, `[::1]`, any port) or the request's own `*.workers.dev` origin, never the request's Host as such; anything else is 403. A browser that is the client itself (no web page) sends no `Origin`; a token is still needed either way. Tools are the `/api/v1` routes, generated: `api::tool_name` is an exhaustive match, so a route added without a decision does not compile; only `Reference` (`tools/list` is the schema), `MediaUpload` and `MediaOriginal` (raw bytes do not fit JSON) and the session-only user-admin routes (MCP is token only) are left out. Input schemas, descriptions (`PATCH /api/v1/posts/{id}; needs post.write; ...`) and annotations (`readOnlyHint` on GET, `destructiveHint` on DELETE) come from the table; `tools/list` shows only tools the token's access allows. A call is split back into path, query and body and run by the same `v1::dispatch`, so validation, `expected_version`, permissions (`also`, session-only settings) and the system log are those of HTTP. Refusals of a call (forbidden, invalid, conflict) are tool results with `isError` and `structuredContent` = the API's error JSON, as the spec advises, so the model sees them and can retry; only protocol faults (unknown method or tool, bad params shape) are JSON-RPC errors. Every error carries `data: {"error": <stable code>, "field"?}`; there is no 405 code, so `GET /mcp` says `api.not_found` like a wrong method on `/api/v1`, and the 405 comes before the token check (it reveals nothing). The envelope (`params`, `arguments`) takes two of the parser's 16 depth levels and shares its value cap, so a JSON setting or option value may nest two levels less than over HTTP, and past those caps the whole message is refused (400 or 413), not answered as a tool error. Resources: every guide as `plumblog://guides/<name>` (`text/markdown`), embedded by the build helper `crates/guides_embed.rs` the CLI uses too. No prompts.

At-least-once: write routes (not built yet) will send attempt 1 right after the response (`waitUntil`, at most 2 per request); today attempt 1 is made by the cron run (in the same run for cron-published posts). Then retries +10 min, +1 h, +6 h from cron, then failed; the same `webhook-id` and body on every retry, so receivers dedupe by id. Only `https` to a public name or public IP (no loopback, private, link-local or reserved names, no userinfo, no odd IP spellings); no redirects followed, 10 s timeout, body not read. The URL is checked at creation and again before every send. Each attempt is one `webhook.delivery` log entry with the host only.

## System log

- Owner-only page in Settings: a readable timeline of what the system did, with filters (type, user, date) and a request id on each entry.
- Recorded: sign-ins and failures, content changes (who, what), settings/theme/plugin changes, deploys and migrations, scheduled jobs, webhook deliveries, automatic plugin disables, errors with a plain message and an error code.
- Never recorded: page views, passwords, tokens, personal data beyond the acting user.
- Stored in D1 with a retention cap (age and row count) so it stays inside free-plan write limits; one write per event, never per view.
- Worker logs carry the same request id, so an AI can go from an admin entry to the full trace.
- Each request has one id (`cf-ray`, else generated); every event and Worker log line from that request carries it.
- Events are built through methods that redact, before storage. A field whose name says secret or personal data (`password`, `token`, `setupCode`, `x-api-key`, `clientIp`, `x-forwarded-for`, `userEmail`..., matched on the full name in any spelling) is replaced whole. In every other value, credentials (JWTs, key prefixes, random-looking strings), emails and IPs (with ports, in lists, IPv4-mapped IPv6) are replaced where they occur (percent-decoded first), as is whatever follows a secret name inside a value: URL userinfo and parameters, `name: value` / `name=value` text, JSON values (single quotes too, and JSON escaped inside a string, up to 4 levels; deeper is redacted whole). Subjects skip only the random-string guesser, so titles and dated slugs stay readable. Request and job code log through `syslog::record`, which cannot fail: a storage error becomes one Worker log line, never a failed request. The stored marker is `{redacted}`; the admin shows the locale key `syslog.redacted` for it. Subjects and values are capped at 200 characters, 8 fields per event. Severity comes from the kind, raised to warning when an error code is attached.
- Retention defaults to 90 days and 10,000 rows, pruned by the daily run of the cron trigger (see Platform), never per event. One run deletes at most 2,000 rows, oldest first, so it stays well inside the free plan's daily writes; a backlog drains over later runs. Each run leaves one `job.run` entry saying how many rows went; failing to write it never stops the prune. Subject and fields share one `detail` column (subject line, then `key<TAB>value` lines, escaped), redacted again when read.
- Read (issue #11): `GET /api/v1/log` (`syslog.view`, owner only; MCP tool `log_list`) answers `log_page`, newest first, keyset-paged by `(at_ms, id)` (opaque `cursor`, `limit` 1-100). Optional filters: `kind`, `level` (`warning` or `error` = minimum severity; `info` is no filter), `code` (error code), `actor` (user id), `from` (inclusive) and `to` (exclusive) in ms, and `q` (1-100 chars: a request id exactly, or text in the subject or a field, ASCII case-insensitive, `%` and `_` literal). Each entry carries its `level`, the actor's current display name (null for the system or a deleted user) and values as stored (`{redacted}` stays). The SQL holds only the filters present, so `kind`, `actor` and dates use their index (`system_log_kind`, `system_log_actor`, `system_log_at`), all in order with no sort (plan test in `d1/log_sql.rs`); level, code and text have no index and walk `system_log_at` newest first, at most the retention cap of 10,000 rows. `q` matches the stored text, which was redacted when written; read-time redaction only catches what an older version let through, so an owner could probe such a leftover with `q`: accepted, as only the owner reads the log.

| Reader page CSS (inlined) | <= 15 KB |

| Admin CSS, gzip | <= 20 KB |
| Lighthouse (mobile + desktop, sample content) | 100, CLS 0 |
| API request body: post create/update (whole JSON body; ~20k words with code, math and 50 images is about 130 KB) | <= 160 KiB |
| API request body: media upload (the original image, raw bytes) | <= 20 MiB |
| API request body: every other route | <= 8 KiB |
| Pushed theme `theme.json` (`pushed::MAX_DOCUMENT`; the default theme's is about 77 KB) | <= 256 KiB |

CPU budgets (10 ms per request on the Worker free plan; wasm runs 1.5-3x slower than native, so natively: a 5,000-word post renders in under 2 ms, a 160 KiB JSON body parses in under 1 ms, a reader page renders in under 2 ms, one server-side PBKDF2 hash costs far less than 10 ms). Wall time on a shared CI runner is a poor clock, so `scripts/check` never gates on those numbers. It gates on work and scaling: counted regex calls for the theme highlighter (the admin paste converter's scaling test is handled in #73), and for Rust (no `unsafe`, so no counting allocator) the best time of a 4x larger input staying under 10x (linear is 4x, quadratic 16x), plus bounds that catch a uniform slowdown (Rust perf tests: the best time must stay under 8x a reference workload, a serial hash of the same bytes, measured interleaved in the same run, so a slow or throttled machine slows both sides and a 10x slowdown of the code under test fails; normal ratio 0.9-1.5 in the release run that enforces it for JSON and markdown (the debug workspace run keeps only their scaling checks, as its ratio measures the compiler), 1.0-1.9 for the debug-only page test; theme highlighter: 300 ms, 5x CI; PBKDF2 per hash: 5 ms, 50x, as workerd runs it natively). The real budgets are measured by `scripts/perf` (a table; CI prints it in a non-gating step; `scripts/perf --strict` enforces them on a machine that is not shared) and, in workerd, by the PBKDF2 line of `scripts/worker-test`. The budgets themselves are unchanged.

Media uploads are not hashed in the Worker: SHA-256 of a 20 MiB body through WebCrypto measured 6.8-7.5 ms in `wrangler dev` (M3 Max, load under 10, best of 3, on the bytes already in JS), on top of about 4 ms to copy the body out of wasm, so with parsing and the R2 and D1 writes a large upload would pass the 10 ms budget. The client hashes and R2 verifies the hash on put (issue #60).

The `theme.json` cap comes from the cold load, which the first request of every isolate pays: parse plus theme load measured natively at 0.6 ms for the default (77 KB), 2.4 ms at 256 KiB, 5.3 ms at 512 KiB and 11.8 ms at 1 MiB, linear (`theme_load_cost` in `crates/worker` theme_runtime, `--ignored`, release). Under `wrangler dev` (worker-test, cold isolate, local clock) the load reads 16 ms for a 77 KB theme and 24 ms at the cap: a fixed cold cost plus about 8 ms for the extra 180 KB. The cap keeps that size-dependent part to a few ms; 1 MiB would add about 4x as much. `blog theme check` and `push` refuse a bigger theme; the Worker refuses one by `Content-Length` and by the bytes it reads, logs `theme.pushed_invalid` and renders the default.

The editor chunk is near its line (110.7 of 110 KB after part C): new editor features load as their own lazy chunk, as the paste converter does, never into the editor chunk.

The embedded default theme and the renderer (for `blog theme check | dev`) made the `blog` binary about 1.8 MB larger; the Worker wasm is within its 1 MiB budget (`scripts/check` prints the figure). The Worker links `serde_json` already but not `toml`, `toml_parser` or `toml_datetime`: `scripts/check` fails if `cargo tree -p plumblog-worker --target wasm32-unknown-unknown -e normal` lists any of them, and the `toml` features are enabled only by `blog`, the Worker's build script and tests.

## Release

Owners never need Rust or Node: they download `blog`, and `blog` downloads the rest. Names and formats are fixed by `scripts/package-release` and `.github/workflows/release.yml`; the CLI side is `crates/cli/src/release/`.

- Files on each GitHub release `vX.Y.Z`: `plumblog-bundle-vX.Y.Z.tar.gz` (the release bundle above, with `bundle.json`), `blog-vX.Y.Z-<target>.tar.gz` (`.zip` on Windows; `blog` or `blog.exe` and LICENSE at the top) for aarch64/x86_64 macOS, aarch64/x86_64 Linux (musl) and x86_64 Windows, `SHA256SUMS` (sha256sum format, every file) and `SHA256SUMS.minisig`.
- Trust chain. `blog` is built with `PLUMBLOG_BUNDLE_SHA256`, the SHA-256 of the exact bundle archive uploaded, baked by `crates/cli/build.rs` (not 64 hex = build error; unset = dev build). `blog deploy` downloads the bundle once into `~/.cache/plumblog/bundles/vX.Y.Z/` (`$XDG_CACHE_HOME`, `%LOCALAPPDATA%` on Windows), checks the hash before unpacking anything, then unpacks in memory: only regular files and folders under `worker/`, `assets/`, `migrations/` plus `bundle.json`; `..`, absolute or drive paths, links and device files are refused; every file must match `bundle.json` and none may be missing; `bundle.json`'s version must equal the CLI's. The unpacked folder is written to a temp folder and renamed into place; the verified archive is reused. A mismatch (`release.hash_mismatch`) says to delete the cache folder, then to `blog update` or download `blog` again. `blog` itself is trusted through `SHA256SUMS`, signed with minisign's legacy pure-Ed25519 algorithm (`Ed`) by the key whose public half is `release/minisign.pub`, embedded with `include_str!` (`PLACEHOLDER` until the owner makes the key: `blog update` refuses with `update.no_key`, the release workflow fails). GitHub build attestations on every file are a second, independent check (`gh attestation verify`).
- `blog backup [--no-media] [--out <dir>]` (`crates/cli/src/backup.rs`) needs a set-up folder and holds `.blog-deploy.lock`; it never deploys. It says the site stays up and the reads count against D1's daily limit, takes a Time Travel bookmark, then writes the same dump as `blog deploy --export` (`dump::export`, into `<dir>/<utc>-<database>.sql`, 0600; `<dir>` defaults to `backups/`). Media: `SELECT id, r2_key, bytes, variants_json FROM media` in pages of 100 by `id`; every original and variant key must be a plain relative path (no empty, `.` or `..` segment, backslash, colon or control character, not `manifest.json`, not ending `.blog-part`), else `backup.key_unsafe` and nothing is requested. Each object is read with `GET /accounts/{id}/r2/buckets/{bucket}/objects/{key}` (wrangler 4.160.0 `getR2Object`: raw bytes, a bare 404 for a miss, key slashes kept and each segment percent-encoded; `Client::get_object`, same token scrubbing and 3-try GET retries as other calls, body held in memory up to the 20 MiB upload cap plus 1 MiB because the client does not stream), checked in memory against the size D1 recorded (`backup.size_mismatch`) and, when the `ETag` is exactly 32 hex digits (a single-part upload's MD5; multipart ETags contain `-` and are not checked, `md-5` crate), against its MD5 (`backup.checksum_mismatch`); only then written to `<dir>/media/<key>.blog-part` and renamed (0600). `<dir>/media/manifest.json` (`key -> {bytes, sha256}`) is rewritten atomically after every object; a file is skipped when its size and SHA-256 match the manifest, so an interrupted run resumes and a finished one fetches nothing. A miss (`backup.object_missing`, the first 20 printed) or a failed object is printed and the run goes on; a rejected token or missing R2 permission stops it. Exit is non-zero (`backup.incomplete`) when any object failed or is missing; with misses the message lists up to 20 keys and says that every file missing usually means a wrong token permission, bucket or object path, not lost files. The run ends by writing the record `{at (unix s), database, media: {objects, bytes, missing, failed} | null, complete}` to `site.local.toml` (`last_backup`) and to the `last_backup` setting (`d1::put_setting`); `store::LAST_BACKUP_KEY` is in `INTERNAL_SETTING_KEYS`: never listed by the settings API or handed to themes, and refused on write and delete, so only `blog` writes it (a future dashboard needs its own read path). `--no-media` skips media (`media: null`, `complete: false`).
- `blog update [--to vX.Y.Z] [--check] [--allow-older]`: the latest release from the GitHub API (no token: the repo is public), never older than the running blog, whether latest or `--to` (`update.downgrade`), unless `--allow-older`, which prints a warning; `SHA256SUMS` and its signature verified (key id, file signature, trusted-comment signature, as `minisign -V`), this target's archive checked against it, the binary written next to the running one and renamed over it (Windows: the running exe is renamed to `blog.old.exe` first and removed on the next run). Then `git pull` for the guides and `blog deploy`.
- Downloads: HTTPS only, timeouts, no credentials, no redirects except GitHub's hop to `objects.githubusercontent.com` or `release-assets.githubusercontent.com`; `PLUMBLOG_RELEASE_BASE` may point only at a loopback test server.
- Key handling: `blog-release keygen release/` (a binary target of `crates/cli`, never shipped) writes the public key, refuses to replace a real one, and prints the secret once (or writes it to a new 0600 file with `--out`). The secret lives only in the GitHub secret `PLUMBLOG_RELEASE_KEY` in the `release` environment (required reviewer, deployments only from tags `v*`; made before the secret is added, since a workflow run otherwise creates the environment unprotected; never a repository secret) and is read only by the signing step, which runs the already-built `blog-release sign` and never cargo, so no build script sees the secret.
- Cutting a release: set the workspace version, merge to main, push tag `vX.Y.Z`; the workflow builds the bundle and every binary with the bundle's hash baked in, signs `SHA256SUMS`, verifies it with the real minisign, attests and uploads to a draft release. A human checks the draft and publishes it; only published releases are "latest".

- 2026-11-28 JS Worker entry: on the Free plan (10 ms CPU) a fresh isolate paid 8-40 ms before reading the request, because workers-rs's `index.js` instantiates the whole 2.4 MB wasm at import. `crates/worker/js/entry.mjs` is now the main module (`scripts/worker-entry` copies it next to `index.js` and sets package.json `main`; `blog deploy`, `scripts/worker-test` and `tools/wrangler.dev.toml` use it) and `import()`s `./index.js` only when it cannot answer: `/healthz` took 0-32 ms CPU before and 0 ms on 30 of 30 requests with a prototype on the test site. It answers `GET /healthz` (Rust's bytes plus `x-plumblog-entry: js`) and GET/HEAD reader-page cache hits: it reads `content_version` from D1, builds the key `<origin>/__page/v<version><theme tag><path>` (no query), and serves the cached response with its body stream untouched, `x-plumblog-cache: hit` and `x-plumblog-entry: js`; a matching `If-None-Match` gets a 304 with only the ETag, compared to the ETag stored on the cached response, so JS never formats an ETag or knows the engine version. The key format and the theme-tag rule are duplicated in JS; `tools/worker-test/entry.test.mjs` pins them to the Rust side. entry.mjs is 1.9 KB gzip (budget 2 KiB). A failed wasm import is not retried (ES modules cache the failure): the isolate fails non-fast-path requests until Cloudflare replaces it.
